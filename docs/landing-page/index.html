Process a Kafka partition in parallel, in order, without adding partitions.

Parallel Consumer decouples concurrency from partition count. Keep your ordering guarantee - per key, per partition, or none at all - and choose the concurrency your workload actually needs.

Get started How it works

Apache-2.0. No licence key, no patent claim, no sidecar. A library you add to a consumer you already have.

01 The ceiling

Partitions are the unit of both concurrency and cost.

A Kafka consumer processes one partition on one thread. If each record takes 20ms, that partition moves 50 records a second, and the only conventional lever is more partitions - which means more cost, more rebalance surface, and a number you can raise but never lower.

  • Partition count outlives the reason it was made.
  • Adding partitions changes key-to-partition assignment, which is a data-layout change, not a tuning knob.

02 The offset map

One slow record does not undo the work behind it.

Parallel Consumer records which offsets completed, not just how far it got. That completion set travels with the commit, so a restart resumes from what is actually outstanding - not from the last record before the first gap.

6,412 records reprocessed

measured: one crash · one stuck record · one 200,000-record partition

Evidence. bench/run-divergence.sh - committed, reproducible, real broker.
Design property. parallel-consumer-core/…/state/PartitionState.java, stated in its own javadoc.

Nine bytes of recovery state

The recovery state for that partition was 9 bytes of commit metadata - a run-length encoding of one incomplete record followed by one run of 199,998 completed ones.

A gap in the offsets is treated the same way as an offset that succeeded: either way there is no work outstanding for it. That is why compacted topics, transaction markers and aborted transactions need no special case - the completion set is built from the records that were actually delivered.

03 A scenario, not a claim

Work is admitted by shard, not by slot.

A partition holds 1 record with key A, then 249 records with key B, then 1,000 records each with a distinct key. Key B is slow. Check the shape against your own key distribution.

What happens

All 1,251 records go into their shards on arrival. The control loop dispatches across every shard, so the 1,000 distinct keys are processed immediately and concurrently while B's records proceed in order on their own shard.

Source. parallel-consumer-core/…/state/ShardManager.java
Wanted. A named integration test asserting exactly this shape, so the scenario is executable rather than described.

The honest limit

Records sharing a key are still serial. That is the ordering guarantee, not a shortcoming - B's 249 records take as long as they take. What is guaranteed is that the other 1,001 do not wait for them.

04 Ordering

Three ordering modes. Pick the guarantee your workload needs.

UNORDERED

Use the whole budget

Uses the full concurrency budget regardless of how your keys are distributed.

KEY

Serial per key, parallel across them

Serial processing within a key, and parallelism across keys.

PARTITION

Keep today's guarantee

Preserves the guarantee you have today while still overlapping work across partitions.

Feature record. docs/features/ordering-modes.yaml

07 Measurement

Measured, with the conditions stated.

Never publish a throughput or efficiency figure without the key distribution, the per-record delay, the concurrency setting, and whether a real broker was in the path. A number whose conditions are stated persuades more than a larger number whose conditions are not.

Excluding broker protocol cost makes a number bigger and makes it mean less. Fetch sizing, batching and commit round trips are a real and large part of what a Kafka consumer does.

Editorial hold - blocked on data

No figures are published here yet. When they are, the chart carries these axes:

  • Key distribution as an axis, not a constant - all-unique, uniform, Zipf, single hot key.
  • Unordered mode across all distributions, where the result should be flat. Flatness is the finding.
  • A real broker in the path, and the protocol cost that comes with it, shown rather than excluded.
