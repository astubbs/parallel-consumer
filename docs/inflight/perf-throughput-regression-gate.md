# A throughput regression gate for the performance lane - collection landed, gating deliberately did not

**The measurement half is done and in use; this note is the gate that should follow it.**

## What exists now

The performance tests emit one `PC-THROUGHPUT` line each, on passing runs as well as failing ones,
via `ThroughputReport` (`grep PC-THROUGHPUT` finds every emitter and every consumer).
`bin/performance-test.sh` collects them, prints them at the end of the lane, and writes
`target/performance-throughput.txt`. Nothing fails on a slow number.

## Why collection alone was worth doing, and why the gate was not rushed

The required `Performance Tests` check gates on wall-clock deadlines. A deadline cannot express how
much slower a tree got - only "slower than the bound, on this runner, today" - so a red timing lane
and a busy runner produce the same signal. That is not theoretical here: a fourfold-to-tenfold
regression sat in this check for weeks, reported on every run, and was read as flakiness every time.
It was found by hand, by measuring rates on two trees.

**A threshold chosen before anyone has seen the real spread would be a guess**, and a flapping
performance gate is worse than none - it gets disabled within a week, and takes the measurement with
it. The observed spread on one idle desktop was already wide across three consecutive runs of the
same tree, which is exactly the reason to collect first and gate second.

## What the gate needs to get right

- **Gate on a factor, not a percentage.** The regression that motivated this was several-fold; a
  coarse bound catches that while ignoring the noise a percentage bound would trip over.
- **Compare like with like, and prefer comparing within one run.** Machine-to-machine variance
  swamps small regressions, and a checked-in baseline is wrong the moment the runner class changes.
  Measuring the branch and its merge-base in the same job costs double lane time and removes the
  largest confound; a stored baseline is the cheaper option and needs to be keyed by runner class
  and treated as a ratchet, the shape the SpotBugs and quarantine registries already use here.
- **Keep reporting on green.** A number recorded only when something fails cannot establish what
  normal looks like. The rule this repo already states is "suppress the violation, never the
  measurement":
  [`../solutions/best-practices/a-timing-bound-used-as-a-correctness-gate-manufactures-its-own-evidence.md`](../solutions/best-practices/a-timing-bound-used-as-a-correctness-gate-manufactures-its-own-evidence.md).
- **An empty collection must fail loudly, not pass quietly.** If no test emits, the lane has measured
  nothing and looks identical to a healthy one. The script says so today; a gate must treat it as an
  error rather than as "no regression detected".

## Not yet wired

`LoadTest`, `LargeVolumeInMemoryTests`, `VeryLargeMessageVolumeTest` and `MultiInstanceRebalanceTest`
carry `@Tag("performance")` and do not emit a figure - only the two tests behind the currently red
lanes do. Extending them is mechanical and is the natural first step here, since a gate over two of
the tagged tests measures less than it appears to.


## 2026-09-01: the precondition this note defers on cannot be met by waiting

The state above used to read *"needs a few runs of real spread before a threshold can be chosen from
data"*. That describes something that arrives if you wait. **Nothing accumulates the spread, so it
does not.**

Where a throughput number goes today, end to end:

- `bin/performance-test.sh` writes `target/performance-throughput.txt` inside the runner and prints
  it. The runner is then destroyed.
- **No workflow uploads it.** `grep -rn 'performance-throughput\|PC-THROUGHPUT' .github/workflows/`
  returns nothing; the only `upload-artifact` in that job is guarded `matrix.suite == 'chaos'`.
- So the sole surviving copy is the `PC-THROUGHPUT` lines inside the job log, for as long as GitHub
  keeps logs - and that is exactly the artefact
  `docs/solutions/workflow-issues/gh-run-view-log-truncation.md` says truncates silently when read
  the obvious way.
- There is no `gh-pages` branch and Pages is off, so there is nowhere a series is being kept either.

**This is why the spread figure everyone quotes came from points reconstructed by hand from logs.**
An investigation into whether one number was a regression had to rebuild the distribution from
scratch, which is the cost of not storing it, paid once per investigation.

## One gap, three symptoms

The throughput tests **never run on master**: the lane's job is `if: github.event_name ==
'pull_request'`, and master's push build passes `-Dexcluded.groups=performance,...`. That single fact
is simultaneously

- why there is no baseline series to choose a threshold from,
- why `benchmark-action/github-action-benchmark` cannot simply be switched on - its model is *push to
  the default branch appends to a series, PRs compare against it*, and there would be nothing to
  append,
- and why a like-for-like CI comparison against master has to be **manufactured** with a throwaway PR
  from a branch at master's tip rather than found in history. See
  `docs/handoffs/perf-lane-throughput-shortfall.md`, whose named experiment this constrains.

## The order that unblocks it, cheapest first

1. **Upload `target/performance-throughput.txt` as a run artifact** from the performance lane,
   mirroring the chaos upload three steps above it in the same job. It lands where that one lands: an
   artifact attached to the workflow run, pulled back with `gh run download <run-id> -n <name>`,
   under the same retention the chaos upload sets explicitly.
<!-- file-refs: N/A - target/performance-throughput.txt is generated by bin/performance-test.sh at run time, so it is correctly absent from a clean tree -->

   **Be clear about what this does and does not buy, because the name "artifact" oversells it.** It
   replaces log-scraping with a machine-readable file, which matters given the truncation trap above.
   It is still *per run*, still expires, and still requires somebody to go and gather N runs before
   there is a distribution to look at. It is a stopgap that makes the data retrievable, not a store.
<!-- file-refs: N/A - target/performance-throughput.txt is generated by bin/performance-test.sh at run time, so it is correctly absent from a clean tree -->
2. **Run a throughput subset on master pushes** - probably `MultiInstanceHighVolumeTest` alone rather
   than the whole lane, since master pushes are infrequent but the lane is expensive.
3. **Then keep the numbers in git, which is the only durable option here** - a committed series on a
   data branch. That is what `benchmark-action/github-action-benchmark` automates, and it is also the
   shape this repo already uses whenever state has to survive across runs: the quarantine registry and
   the analyser ratchets are committed files, not artifacts, for exactly this reason. Rolling it by
   hand is a real alternative to the action if the third-party dependency or the write grant is
   unwelcome - the action's value is the chart and the comparison, not the storage, which is a commit.

   Wire it with `fail-on-alert: false` and a loose
   threshold. That is collection, not gating, so it *fits* this note's original decision rather than
   reversing it - and the chart is what finally shows the spread a threshold could be chosen from. It
   needs `contents: write` for its data branch, where the workflow has `contents: read` today; this
   repo is deliberate about that grant, see the security header in
   `.github/workflows/experiments.yml`.

**Operator decision, 2026-09-01: none of that lands here.** CI and measurement infrastructure has
nothing to do with the deadlock fix and must not be gated behind it, so it goes on a branch cut from
master - where it also starts building the series immediately, rather than after a long-lived branch
merges. A series that only begins once the branch under suspicion has landed cannot help judge it.
