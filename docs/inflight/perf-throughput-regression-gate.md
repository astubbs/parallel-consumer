**The measurement half is done and in use; this note is the gate that should follow it.**

## What exists now

The performance tests emit one `PC-THROUGHPUT` line each, on passing runs as well as failing ones,
via `ThroughputReport` (`grep PC-THROUGHPUT` finds every emitter and every consumer).
`bin/performance-test.sh` collects them, prints them at the end of the lane, and writes
`target/performance-throughput.txt`. Nothing fails on a slow number.

## Why collection alone was worth doing, and why the gate was not rushed

The required `Performance Tests` check gates on wall-clock deadlines. A deadline cannot express how
much slower a tree got - only "slower than the bound, on this runner, today" - so a red timing lane
and a busy runner produce the same signal. That is not theoretical here: a fourfold-to-tenfold
regression sat in this check for weeks, reported on every run, and was read as flakiness every time.
It was found by hand, by measuring rates on two trees.

**A threshold chosen before anyone has seen the real spread would be a guess**, and a flapping
performance gate is worse than none - it gets disabled within a week, and takes the measurement with
it. The observed spread on one idle desktop was already wide across three consecutive runs of the
same tree, which is exactly the reason to collect first and gate second.

## What the gate needs to get right

- **Gate on a factor, not a percentage.** The regression that motivated this was several-fold; a
  coarse bound catches that while ignoring the noise a percentage bound would trip over.
- **Compare like with like, and prefer comparing within one run.** Machine-to-machine variance
  swamps small regressions, and a checked-in baseline is wrong the moment the runner class changes.
  Measuring the branch and its merge-base in the same job costs double lane time and removes the
  largest confound; a stored baseline is the cheaper option and needs to be keyed by runner class
  and treated as a ratchet, the shape the SpotBugs and quarantine registries already use here.
- **Keep reporting on green.** A number recorded only when something fails cannot establish what
  normal looks like. The rule this repo already states is "suppress the violation, never the
  measurement":
  [`../solutions/best-practices/a-timing-bound-used-as-a-correctness-gate-manufactures-its-own-evidence.md`](../solutions/best-practices/a-timing-bound-used-as-a-correctness-gate-manufactures-its-own-evidence.md).
- **An empty collection must fail loudly, not pass quietly.** If no test emits, the lane has measured
  nothing and looks identical to a healthy one. The script says so today; a gate must treat it as an
  error rather than as "no regression detected".

## Not yet wired

`LoadTest`, `LargeVolumeInMemoryTests`, `VeryLargeMessageVolumeTest` and `MultiInstanceRebalanceTest`
carry `@Tag("performance")` and do not emit a figure - only the two tests behind the currently red
lanes do. Extending them is mechanical and is the natural first step here, since a gate over two of
the tagged tests measures less than it appears to.
