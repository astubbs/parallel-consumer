Part 1 — Interaction Model (2026-08-14)

The subject is how the sidecar and its non-Java workers interact — not the transport (gRPC is settled) and not the product scope. The credit-ledger design was rejected before this run began; the question is what replaces it, and how much of the client library survives that choice.

The frame: the wrapper is the layer

"PC in every language" means every language gets the same client wrapper, and to the user it looks native. Java's wrapper is that same layer with one fewer hop — it sits directly on the engine with no protobuf underneath. This is one client model with a missing layer in the Java case, not two architectures, and every idea below is judged against that frame.

Read this first: the verifier was judging a stale document

The fresh-context verifier scored every candidate against docs/plans/2026-08-12-001-feat-language-proxy-plan.md, which still carries the credit model (KD9, KTD9, R23) and its dependents (KD8's many-direct-connections, KTD9's round-robin allocator) as settled. Several "refuted" verdicts rest entirely on contradicting decisions this session has already superseded.

Those verdicts are overruled below, each with its reason stated. Verdicts resting on code or on prior-art accuracy are retained — and two of them materially downgraded ideas I was enthusiastic about.

Grounding Context

Codebase (verified this run, with a second pass by the verifier):

  • ExternalEngine forces the worker pool to size 1 — external engines do not use a thread pool; one thread dispatches. Vert.x and Reactor already ride this seam.
  • getTargetAmountOfRecordsInFlight() == getMaxConcurrency() * getBatchSize(), and ExternalEngine.getTargetOutForProcessing() returns exactly that — so max concurrency is already how the existing external engines bound in-flight work, not a thread-pool size.
  • calculateQuantityToRequest() computes target − numberRecordsOutForProcessing every control-loop pass, so an engine can vary its target dynamically.
  • On the async path, ExternalEngine withholds the mailbox entry so each WorkContainer completes independently. Per-record outcomes from a batch are therefore possible — the old plan's claim to the contrary does not hold on this path.
  • ProcessingShard permits at most one in-flight record per shard under restricted ordering. Key ordering is enforced host-side, for free.
  • WorkContainer.markAbandoned(deliveryCount) + isReturnForSupersededDelivery() already implement verdict-free return and late-duplicate rejection, in-process.
  • Verifier addition: WorkManager.numberRecordsOutForProcessing is a live accumulator with five mutation sites, and the silent-stall learning attributes a real bug to drift in exactly that counter.

External prior art — Apache Beam's Fn API (runner owns scheduling, per-language SDK harness runs user code, gRPC between them; Python fans out to one subprocess per core for the GIL; bundles retry whole, per-item outcomes deliberately rejected) · Temporal (shared Rust sdk-core with thin bindings; workers poll; host-side "slots") · Ray (node-local daemon owns worker lifecycle; language driver never spawns) · Envoy ext_proc (stream per request; processor controls granularity) · Bytewax (Rust core, Python in-process FFI, no IPC) · Dask (batch assignment to least-busy worker).

Standing constraint: four consecutive review rounds on the flow-control / in-flight-accounting seam each produced the next round's defect. The recorded instruction is to change a decision rather than patch that seam again — which is what this whole exercise is.

Ranked Ideas

1

Reconnect reconciles a manifest — a dropped pipe is not a dead worker

failure & recoveryConfidence: HighComplexity: Mexternal + direct

Connection loss does not immediately abandon that connection's records. The sidecar protects them for a bounded grace window; the reconnecting client opens with a manifest of tokens its live workers still hold; the sidecar reconciles — still-current tokens stay in flight untouched, superseded ones are ordered dropped, absent ones are abandoned with attempt count unchanged. Only window expiry abandons.

Basis
external: ATC lost-communications procedure — losing radio contact does not mean losing the aircraft. The controller protects the clearance rather than reassigning the level; reassigning on contact loss is the accident-causing move. direct: A TCP drop is information about the pipe, not the executor.
Why it matters — this is the run's most valuable finding The current requirement says a closed connection returns that worker's records immediately. The verifier traced it: that keeps the sidecar's bookkeeping consistent, but does nothing to stop two physical workers running the same key's user code concurrently during a transient blip — the original worker is still alive and finishing while the redelivered copy starts elsewhere. Every host-side invariant reads green while the one guarantee the product is sold on is violated in reality.
Status A live correctness gap in a requirement currently treated as decided. This is not a preference — it should be escalated regardless of which other ideas are adopted.
2

One connection, fan-out inside the client (the admin model)

work hand-outConfidence: HighComplexity: MSETTLED

The protocol permits exactly one connection per application. An admin holds the stream and relays to its workers — a goroutine talking to worker goroutines in Go, a process talking to worker processes in Python. Identical shape in both languages, so the client translates with far less error surface, and the sidecar never learns whether the far end is threads or processes.

Basis
external: Beam's SDK harness does exactly this — one harness fans out internally, threads for Java/Go and one subprocess per core for Python because of the GIL, muxed by instruction ID. Same GIL problem, solved without any multi-connection protocol. Correction retained from the verifier: Beam actually uses several distinct gRPC services per harness (control, data, state, logging), not literally one connection — the surviving idea is "one harness, internal fan-out", not "one socket".
Why it matters Every piece of proxy state this project has fought — round-robin allocation, no-starvation guarantees, the "no other worker was lost in the same window" attribution clause — is a consequence of several connections. One connection deletes the seam rather than patching it.
Honest cost Fan-out bugs move inside the client, invisible to the sidecar, and get written twice — but in each language's native idiom (multiprocessing, worker goroutines), which is the cheapest thing to write twice.
Verifier verdict overruled
Marked "refuted" for contradicting the many-direct-connections decision — but that decision is downstream of the credit model this session rejected. Overruled: it contradicts a superseded premise, and it is the user's own proposal, independently matched by the closest prior art in existence.
3

An epoch per delivery — fencing borrowed from Kafka's own exactly-once model

client shapefailure & recoveryConfidence: HighComplexity: SSETTLED

Every dispatched record carries an epoch. A dead client is fenced and the epoch increments when the record is handed to another worker; a report naming a superseded epoch is discarded. The worker echoes the epoch back verbatim and keeps no request map, no callback table, no dedupe cache — the sidecar is the only party holding state.

Scope of the fence — state it plainly
Fences reports and Kafka-side effects: workers never produce directly, so output travels back through the engine and the sidecar produces behind one epoch check — which is what keeps exactly-once entirely on the JVM side, one producer, one transactional id. It does not fence a worker's external side effects (a database write, an HTTP call). No system fences those; the protocol should not imply otherwise.
Basis
direct: markAbandoned(deliveryCount) and isReturnForSupersededDelivery() already implement precisely this rule in-process — confirmed by the verifier by reading the file. The "capture the delivery at dispatch, never read it at return" discipline becomes structural when the token is literally the thing handed out. external: Court docket numbers — the parties keep no ledger; the number is printed on the paper they were handed, and a filing citing a closed matter is rejected at intake.
Why it matters A stateless client cannot have a state bug. It also reuses logic that was expensive to get right rather than re-deriving it per language — and "echo these bytes" is the one instruction an author writing from the spec alone cannot misread.
4

Dispatch a wave of independent shard-heads, report each record separately

work hand-outConfidence: HighComplexity: Mdirect + external

Send several records from different shards in one message for wire efficiency, but report each independently as it completes. Because a shard holds at most one in-flight record, a wave never contains two records of the same key — so there is nothing to serialize and no shared verdict to construct.

Basis
direct: The async path completes each work container independently — verifier-confirmed at the Vert.x hook and at the shard's one-per-shard break. external: Beam bundles many elements and discards the whole bundle if any element fails, having deliberately rejected per-item outcome tracking as not worth the complexity.
Why it matters This is a capability the closest prior art declined to build. It amortises wire cost without inheriting all-or-nothing retry, and it makes the client's job the same three steps in every language: unpack wave, dispatch, report per record.
5

The engine puppeteers; the client spawns — policy in the sidecar, mechanism in the client

lifecycle & supervisionConfidence: HighComplexity: MSETTLED

The user's app starts the sidecar. The sidecar decides how many executors and when, and says so in a message. The client library — already inside the user's process, holding the user's function — does the actual spawning with its own language's native mechanism. The engine never learns what the function is, or what a function even is; it just asks for executors.

Why this beats both of the options it replaces
Against client supervises the sidecar: the bind-race election disappears, because one app process starts one sidecar — there is nothing to elect. The detached process group disappears too; it only existed so the sidecar could outlive whichever worker won the race, and the app is now the parent that should own it. Against sidecar spawns the workers: the sidecar would have needed to know how to start the user's program, which is deploy-time configuration that fails late — and it could only spawn a command, forcing the user's function to be an importable name rather than a closure. Keeping the mechanism client-side dissolves both.
What it settles downstream
Config travels connect-time over the protocol, expressed in the user's own language — no config files, no environment variables, no shell. Generated stubs are not a translation layer. Max concurrency is set by the app, sent to the engine, and used as the in-flight ceiling — which is already exactly what maxConcurrency × batchSize means to an external engine, so no core change is needed for it. App shutdown shuts the sidecar down: drain in-flight work within the bounded timeout, commit, leave the group. The no-connection grace period is no longer needed at all — the app's death is the signal, rather than something to infer from zero connections.
Residuals
SIGKILL backstop — if the app is killed outright nothing runs, so the sidecar must watch its parent and exit on its own (closing pipe, or PR_SET_PDEATHSIG on Linux). Otherwise a JVM leaks while still holding group membership, and partitions do not rebalance until the session timeout. Python spawn-method — fork inherits the closure for free; spawn (default on macOS and Windows) re-imports and needs something picklable. An API-shape and documentation question, not an architectural one. Credentials over the wire — see the settled list below; this revises a requirement rather than violating it, but it has to be written down.
6

A liveness lease, explicitly not a processing deadline

backpressurefailure & recoveryConfidence: HighComplexity: Mdirect

Assume the worker may hang, loop forever, or never report. A lease is attached at dispatch and extended by heartbeats on the stream; on expiry the record is abandoned with attempt count unchanged. Poison detection reads the delivery count that already increments on every hand-out. A legitimately slow worker heartbeats and holds its record indefinitely; a dead one does not.

Basis
direct: Verifier confirmed there is no wall-clock processing deadline anywhere in this path — the slow-work threshold only warns, never abandons. That is deliberate: "a record stays in flight until your function returns; there is no clock" is PC's stated differentiator against Share Groups, whose acquisition-lock timeout genuinely is a processing clock.
Why it matters Folds crash, hang, infinite loop and worker bug into one host-side path needing zero worker cooperation — therefore zero per-language code. The distinction from a processing deadline is the whole game: build the wrong one and the product loses its differentiator.

Settled during this run

  • The wrapper is the layer; Java is the degenerate case. One client model, with the protobuf hop absent in Java rather than a second architecture.
  • The engine puppeteers, the client spawns. Policy in the sidecar, mechanism in the client — survivor 5.
  • Workers never produce to Kafka directly. Output travels back through the engine and the sidecar produces. This is what lets survivor 3's epoch check carry exactly-once on its own — one producer, one transactional id, one fence.
  • Configuration is code, delivered connect-time over the protocol. No config files, no environment variables, no shell. Lean on the target language's own tooling; generated stubs do not count as a translation layer.
  • Max concurrency keeps its existing meaning. Set by the app, sent to the engine, used as the in-flight ceiling — already what it means to ExternalEngine. Two earlier proposals to withdraw it were both wrong.
  • App shutdown shuts down the sidecar. Drain within the bounded timeout, commit, leave the group. Plus a parent-death backstop for SIGKILL.
  • Native shared library: dead end. See the rejection table.

Part 2 — HTTP Dialect, Generated Clients, REST Proxy Compatibility (2026-08-17)

The subject is the HTTP strategy: a native HTTP dialect of the frozen protocol, clients generated from an HTTP specification rather than hand-written, and a Confluent REST Proxy compatible surface. This is the "proper ideation pass" that docs/inflight/next-http-strategy-ideas.md says it is owed — the seed notes' option space is the starting line, and every idea below is held to advancing beyond it. 44 raw candidates from five frames → merged and adversarially verified → 7 survivors.

The run's headline: the REST Proxy feasibility unknown is settled — compatible-and-beneficial

The seed notes parked compatibility on one unknown: "if their endpoint hands out one message per partition assignment, a compatible implementation may be unable to hand out several from one partition … compatibility without the concurrency benefit, i.e. pointless. Read their API before believing either way." This run read the primary sources (Confluent's v2 API reference, the kafka-rest New-Consumer-API-Design wiki, the v3 openapi.yaml).

Verdict: the contract has room. v2's only client-visible unit of progress is a cumulative per-partition offset watermark (POST …/offsets, same shape as commitSync) — exactly what Parallel Consumer already computes internally from its offset map. No per-record ack exists in their contract, so beyond-partition concurrency is purely server-side scheduling, invisible to a well-behaved client. Two obligations: records within one /records reply must arrive in offset order, and auto-commit must mean "commit the internally-verified-safe watermark". One caveat: v3 has no consumer data plane at all (monitoring/admin only) — "REST Proxy compatible" necessarily means emulating v2.

  • The engine seam is ProxyProcessor extends ExternalEngine; admission is SingleConnectionGuard (one connection, generation counter) + AuthorityAllowlistInterceptor; the session already outlives connections (ConfigureHandler re-routes dispatch at whichever stream holds the session).

1

REST Proxy v2 compat is real: one gateway, one conformance row, proven with their own tooling

rest-proxy-compatConfidence: HighComplexity: Mdirect + external

Build the v2-compatible consumer surface as a gateway that is a client of the native engine seam (the XWayland rule: the legacy protocol lives entirely outside the core, with no private hooks — its existence proves the seam sufficient). GET …/records long-polls the engine's push buffer and replies in offset order; POST …/offsets with watermark X becomes per-record success for fetched records ≤ X; auto-commit commits the internally-verified-safe watermark. Prove the compatibility claim the pgwire way: drive the conformance row with Confluent's own v2 client, and run the same scenarios differentially against a real REST Proxy container — the divergence report is the compatibility claim, datable and falsifiable.

Basis
direct: Primary-source contract read (this run): v2 POST …/offsets commits a cumulative per-partition watermark, "identical in shape to commitSync"; no per-record ack exists; v3 ships no consumer data plane. Sources: docs.confluent.io kafka-rest API reference; kafka-rest New-Consumer-API-Design wiki; kafka-rest api/v3/openapi.yaml. external: CockroachDB's Postgres-compat program (run the incumbent's tests, publish a feature matrix, fail loudly on unsupported features); Karapace already treats the v2 wire format as a standard worth cloning 1:1.
Rationale This flips the seed's recorded "possibly pointless" unknown into "provably beneficial with almost no new logic": the hardest-looking piece — reconciling out-of-order per-record completion into a single number an offset-committing client understands — is the offset map PC already maintains. And the sidecar's single-instance shape makes REST Proxy's most-cited operational hazard (sticky instance affinity, kafka-rest#1057/#212, Strimzi's multi-replica warning) impossible by construction: there is nothing to pin. A migrating user changes a hostname and gains key-ordered concurrency beyond partitions.
Downsides It is a pull shim, and it must stay one — quarantined in its own module so pull semantics never leak into the native dialect (the recorded concession). Long-poll latency is inherent to the v2 shape. "Run their tests" may need harness adaptation; the differential container run stands on its own if so. A lagging record caps the advertised watermark for its partition — standard cumulative-commit behaviour, but worth documenting for migrants expecting REST Proxy's simpler internals.
2

Compat is where "generated clients" lives — the codegen ask lands on the pull surface, by design

client-generationConfidence: HighComplexity: Sdirect + external

The ask behind this run — clients generated from the HTTP API — splits cleanly once the codegen landscape is faced honestly: OpenAPI generators produce excellent request/response clients and essentially no streaming ones (no major generator treats SSE or long-poll as first-class). A GET/PUT resource surface is almost entirely generatable; an SSE push surface is mostly not. So put the generated-multilingual-clients story where generation actually works — the compat/resource surface — and keep the native dialect's per-language surface deliberately thin: a small hand-written SSE transport feeding the shared, dialect-agnostic controller. State this scope split up front, before anyone estimates "generate 11 HTTP clients" as one line item.

Basis
direct: The seed's own caveat — "OpenAPI describes request/response well and streaming poorly … the dispatch stream is the part a generator will not give you" — and its corollary: "a GET/PUT resource model is almost entirely generatable … the generator gets the boring half, which is exactly the half compatibility needs" (next-http-strategy-ideas.md §4b). external: Speakeasy/Fern/Stainless/Kiota comparisons (this run): none claims first-class SSE/long-poll generation.
Rationale This dissolves the apparent conflict between the user's ask and the settled push model. Nothing pull-shaped becomes native — the pull surface exists anyway for compatibility, and it happens to be the one place the generated-client promise is fully keepable. The native dialect keeps the controller (the hard, correctness-bearing part — "every client that went wrong in this project went wrong exactly there") hand-written and shared, exactly as the gRPC clients do today.
Downsides "Generated clients" becomes a nuanced claim rather than a slogan — the docs must say which surface generates fully. Languages wanting native-dialect HTTP still hand-write the SSE consumption. If a streaming-capable generator matures (Connect RPC's coverage grows, or OpenAPI's SSE story improves), the split should be revisited.
3

Session-scoped lease + one termination vocabulary — the re-spec that blocks every HTTP wire shape

native-dialect-wire-shapeConfidence: HighComplexity: Mdirect + external

The frozen spec says "the lease is connection-scoped" — a definition with no referent once dispatch (SSE) and reports (POSTs) travel different connections, which the seed already flags: "the two halves can disagree about liveness." Adopt the transponder rule from aviation's lost-comms doctrine: contact on any channel is proof of life. Redefine the lease as session-scoped — any authenticated session traffic (a report POST counts) extends it; a dead SSE stream with live POSTs is a reconnect-the-push-channel event, not session death — and gRPC's connection-scoped lease becomes the degenerate case. Pair it with one dialect-neutral termination taxonomy (who ended the session, why, is reconnect legal) that each transport maps its native signals into. Prove it with a java-http conformance row extending the existing control-arm ladder (core → java-direct → java-grpc → java-http: transport isolated from language by construction), and a curl-shell binding as a falsifiable simplicity ceiling — if ~100 lines of shell cannot pass the scenarios, the wire is too complex.

Basis
direct: protocol-specification.md: "the lease is connection-scoped" (verified this run); parked-http-dialect-and-generated-clients.md: "dispatch and reports are separate, so the two halves can disagree about liveness" and "Termination must normalise … it needs one vocabulary behind it." external: Aviation lost-communications doctrine — voice and transponder are separate channels; either one is proof of life, and only total silence triggers the protection procedure.
Rationale This is the one place the frozen protocol's vocabulary literally cannot survive transliteration to HTTP, and it touches the protocol's most safety-critical semantics — premature record reclamation on one side, zombie sessions on the other. Deciding the liveness unit before the first HTTP client exists prevents the two dialects diverging where divergence hurts most. It also cheapens clients: a reporting worker needs no separate heartbeat timer. The session already outlives connections (ConfigureHandler's routing) — the lease vocabulary just hasn't caught up with the protocol's own reconnect design.
Downsides Amends documented semantics of the frozen spec — additive in wire terms (no message changes required for gRPC) but a real semantic re-spec that existing bindings must re-verify against. The transponder rule makes lease expiry marginally slower to detect for a client whose only live channel is reports (by design). The curl-shell binding is a maintenance commitment.
4

Derive, don't author: one frozen contract, N derived encodings

client-generationConfidence: HighComplexity: Mdirect + external

Never hand-author a second frozen contract. Derive the OpenAPI document from the already-frozen .proto — transcoding annotations (grpc-gateway / Connect style google.api.http) for paths, proto3's canonical JSON mapping for bodies — and commit it as a build artifact: the generated document regenerating differently is a build failure, not a review comment. bin/check-proto-breaking.sh remains the single freeze gate; the existing capability-versioning rule automatically governs the HTTP contract too. Zero new governance surface for the second dialect.

Basis
direct: bin/check-proto-breaking.sh: "after the freeze the wire may only GAIN, never change" (verified this run) — the discipline exists once and should not be re-implemented for a sibling document. external: ASN.1's encoding rules (X.690/691/693): one schema, multiple wire encodings derived by published rule, so encodings cannot drift — and proto3's canonical JSON mapping is the same construct already standardized for this schema language. Envoy/grpc-gateway transcoding derives REST + OpenAPI from annotated protos in production systems today.
Rationale The freeze discipline exists because a moving spec makes ten clients diverge ten ways; a second hand-frozen spec reintroduces that hazard as slow drift between two frozen documents with two gates — drift neither gate can see. Deriving mechanically means there is nothing new to govern, and the annotations do not touch wire bytes, so the frozen-wire rule is respected.
Downsides / alternatives recorded Transcoding annotations constrain URL/verb design to what the mapping can express — a REST-Proxy-shaped compat surface (survivor 1) stays a separately-described emulation, since its wire is Confluent's, not ours. Two alternatives were weighed: a transport-neutral core spec with per-dialect binding chapters (sound, heavier restructuring of the frozen document), and adopting Connect RPC wholesale (verified this run: official codegen covers roughly five of the eleven target languages — real, but overstated as a full answer; recorded as a partial option, not the default).
5

Control plane / observation plane — one ruling that settles the listener, the dashboard, and the browser

entry-points-sessionConfidence: MedComplexity: Ldirect + reasoned

Split every HTTP surface into two planes with independent postures, decided once. The control plane (Configure, dispatch, reports) is never browser-reachable — ideally not even TCP: bind it to a Unix domain socket (curl --unix-socket; the Docker API precedent), where filesystem permissions are kernel-enforced authorization. The observation plane (session state, offset frontier, in-flight-per-key as SSE, health) is read-only, carries no credentials, and is designed for a browser deliberately — CORS and origin rules answered once. The parked dashboard becomes the observation plane's first client, dogfooding the HTTP dialect daily; a /.well-known descriptor enumerating the surfaces and their postures gives discovery a single home. This answers "one listener, two purposes — decide before either is built" with a ruling both parked workstreams can build on, and gives the browser its first safe rung without touching the recorded "never a control default" guidance.

Basis
direct: "One listener, two purposes — decide that before either is built, not after" and the browser-surface warning that it "breaks completely" the four load-bearing sidecar constraints (next-http-strategy-ideas.md §4e/§4f; parked-sidecar-embeds-web-gui.md). direct: JDK 16+ UnixDomainSocketAddress is cross-platform in java.nio — independent of netty's transports, so a plain HTTP server dodges the netty-kqueue gap that blocks gRPC-over-UDS on macOS (verified this run; macOS peer credentials via LOCAL_PEERCRED rather than Linux's SO_PEERCRED). external: Docker's API on a unix socket; CUPS serving IPP and a web UI from one loopback daemon for 25 years with Host-header validation — the same authority-allowlist posture this project built.
Rationale The multi-entry-point questions (§4e/§4f) are the design work this branch says is "more interesting than any individual dialect" — and one asymmetric ruling answers most of them: the plane a surface belongs to determines its posture, its listener, and whether it may ever own the session. The UDS control plane upgrades the same-host security story (kernel-verified peer identity where the TCP allowlist trusts the client's self-report), and a UDS-only /debug/session endpoint gives operators the curl-able incident view they currently lack without widening the TCP surface.
Downsides The largest design surface in the set — two postures to specify and keep honest, and the observation plane's browser exposure still owes the CORS/DNS-rebinding write-up before anything binds off loopback. Windows UDS support (AF_UNIX exists since 2018) needs verifying for the control plane's default there. Med confidence: the plane split is well-grounded; "control on UDS by default" needs a spike.
6

Admission gets a real identity: a session secret on the wire, an inherited socket underneath

security-postureentry-points-sessionConfidence: HighComplexity: Mdirect + external

Two complementary mechanisms, both additive. (a) Session-continuity secret: Configured returns a random bearer token; manifests, reports and heartbeats present it; reconnect without it is refused. HTTP needs a session identifier anyway — separate requests must name their session — so mint it as a capability and backport it to gRPC, closing the recorded KTD11 reconnect falsifier ("R41 hands the admission slot back on every reconnect, and nothing re-authenticates the peer"). It is also the answer to "which client owns this session" once entry points multiply: the owner is the bearer, not whoever holds a connection. (b) Admission by inheritance: the spawner creates a connected socketpair and passes one end to the sidecar as an inherited fd (the LSP-stdio / inetd / systemd socket-activation model). No listener ever exists, so the first-vs-parent race — the half of KTD11 no allowlist can close — cannot occur; "only my parent can reach me" becomes a property of the kernel's fd table.

Basis
direct: The plan's own KTD11 falsifier, verified this run: over loopback TCP "there is no peer-credential mechanism at all … any local process that connects before the spawning application does is indistinguishable from it", and reconnect re-opens the window for the process lifetime. external: LSP's default stdio transport and inetd/systemd fd passing — decades-old sidecar-shaped systems whose admission model is inheritance, not racing to a port.
Rationale One small wire addition and one transport mode close both halves of the only recorded unmitigated gap in the security posture — and they are exactly the primitives the HTTP dialect and the multi-entry-point future need anyway (session affinity for split channels; an ownership token for survivor 5's planes). The engine-puppeteers-client-spawns decision already establishes the parent relationship that inheritance authenticates.
Downsides The secret protects reconnect, not first admission (that is what inheritance is for) — the two must ship as a pair to close the gap fully, and the doc must not claim either alone suffices. Inherited-fd mode changes the spawn contract per language (fd passing is awkward in some runtimes) — it should be the default where cheap, an option elsewhere, and the socketpair mode needs a Windows story (named-pipe inheritance) before it is claimed cross-platform.
7

kafka_properties key allowlist — escalate regardless of the HTTP decision

security-postureConfidence: HighComplexity: SESCALATE

The plan records it, and this run verified it live in code: KafkaClientFactory copies the client-supplied kafka_properties map with zero key filtering, and Kafka instantiates class-valued properties reflectively (interceptor.classes, metric.reporters, the LoginModule inside sasl.jaas.config) — so capturing the admission slot escalates from credential theft to arbitrary class instantiation inside the sidecar JVM. Fix it once at the Configure → KafkaClientFactory seam, now, while only gRPC reaches it: every future entry point — native HTTP, compat gateway, anything — inherits the allowlist automatically instead of each dialect's author having to remember it. Per-surface credential policy follows: the HTTP dialect should carry no credentials at all (env/file at spawn), recorded as a first-class row in the spec.

Basis
direct: Plan: "the Kafka client property map arrives over the same socket with no key allowlist … escalates to arbitrary class instantiation inside the sidecar JVM" — marked unactioned, and the more serious of the two. Verified this run against the live code: KafkaClientFactory.production() does new HashMap<>(kafkaProperties) with no filtering.
Rationale Like Part 1's reconnect-manifest finding, this is not a preference between directions — it is a recorded, verified defect whose cheapest fix window is before a second surface multiplies the exposure. It sits at the one seam every dialect must pass through, which is what makes fixing it now compounding rather than merely prudent.
Downsides An allowlist must be curated — legitimate advanced properties (custom partitioners, metric reporters the operator actually wants) need an explicit opt-in path or the proxy breaks real configurations. Small, bounded work; the cost is deciding the list, not writing the code.

Settled during this run

  • The REST Proxy compatibility unknown is settled: compatible-and-beneficial. v2's cumulative watermark is the engine's own offset-map product; beyond-partition concurrency is invisible to the wire contract. v3 has no consumer data plane, so compat means v2. (Primary sources read this run; the seed's "read their API before believing either way" is discharged.)
  • The generated-clients ask splits by surface. Fully generatable where the surface is request/response (compat); thin hand-written transport + shared controller where it streams (native dialect). No generator does SSE first-class — verified across the major vendors.
  • Pull stays quarantined. The hanging-GET native dialect was tested against the settled push rule and refuted — pull exists only behind the compat boundary.
  • A plain HTTP server can reach a Unix socket on macOS. JDK 16+ UnixDomainSocketAddress is netty-independent — the parked gRPC-UDS macOS blocker does not transfer to the HTTP dialect.
