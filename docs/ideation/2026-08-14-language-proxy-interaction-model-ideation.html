The subject is how the sidecar and its non-Java workers interact — not the transport (gRPC is settled) and not the product scope. The credit-ledger design was rejected before this run began; the question is what replaces it, and how much of the client library survives that choice.

The frame: the wrapper is the layer

"PC in every language" means every language gets the same client wrapper, and to the user it looks native. Java's wrapper is that same layer with one fewer hop — it sits directly on the engine with no protobuf underneath. This is one client model with a missing layer in the Java case, not two architectures, and every idea below is judged against that frame.

Read this first: the verifier was judging a stale document

The fresh-context verifier scored every candidate against docs/plans/2026-08-12-001-feat-language-proxy-plan.md, which still carries the credit model (KD9, KTD9, R23) and its dependents (KD8's many-direct-connections, KTD9's round-robin allocator) as settled. Several "refuted" verdicts rest entirely on contradicting decisions this session has already superseded.

Those verdicts are overruled below, each with its reason stated. Verdicts resting on code or on prior-art accuracy are retained — and two of them materially downgraded ideas I was enthusiastic about.

Grounding Context

Codebase (verified this run, with a second pass by the verifier):

  • ExternalEngine forces the worker pool to size 1 — external engines do not use a thread pool; one thread dispatches. Vert.x and Reactor already ride this seam.
  • getTargetAmountOfRecordsInFlight() == getMaxConcurrency() * getBatchSize(), and ExternalEngine.getTargetOutForProcessing() returns exactly that — so max concurrency is already how the existing external engines bound in-flight work, not a thread-pool size.
  • calculateQuantityToRequest() computes target − numberRecordsOutForProcessing every control-loop pass, so an engine can vary its target dynamically.
  • On the async path, ExternalEngine withholds the mailbox entry so each WorkContainer completes independently. Per-record outcomes from a batch are therefore possible — the old plan's claim to the contrary does not hold on this path.
  • ProcessingShard permits at most one in-flight record per shard under restricted ordering. Key ordering is enforced host-side, for free.
  • WorkContainer.markAbandoned(deliveryCount) + isReturnForSupersededDelivery() already implement verdict-free return and late-duplicate rejection, in-process.
  • Verifier addition: WorkManager.numberRecordsOutForProcessing is a live accumulator with five mutation sites, and the silent-stall learning attributes a real bug to drift in exactly that counter.

External prior art — Apache Beam's Fn API (runner owns scheduling, per-language SDK harness runs user code, gRPC between them; Python fans out to one subprocess per core for the GIL; bundles retry whole, per-item outcomes deliberately rejected) · Temporal (shared Rust sdk-core with thin bindings; workers poll; host-side "slots") · Ray (node-local daemon owns worker lifecycle; language driver never spawns) · Envoy ext_proc (stream per request; processor controls granularity) · Bytewax (Rust core, Python in-process FFI, no IPC) · Dask (batch assignment to least-busy worker).

Standing constraint: four consecutive review rounds on the flow-control / in-flight-accounting seam each produced the next round's defect. The recorded instruction is to change a decision rather than patch that seam again — which is what this whole exercise is.

Ranked Ideas

1

Reconnect reconciles a manifest — a dropped pipe is not a dead worker

failure & recoveryConfidence: HighComplexity: Mexternal + direct

Connection loss does not immediately abandon that connection's records. The sidecar protects them for a bounded grace window; the reconnecting client opens with a manifest of tokens its live workers still hold; the sidecar reconciles — still-current tokens stay in flight untouched, superseded ones are ordered dropped, absent ones are abandoned with attempt count unchanged. Only window expiry abandons.

Basis
external: ATC lost-communications procedure — losing radio contact does not mean losing the aircraft. The controller protects the clearance rather than reassigning the level; reassigning on contact loss is the accident-causing move. direct: A TCP drop is information about the pipe, not the executor.
Why it matters — this is the run's most valuable finding The current requirement says a closed connection returns that worker's records immediately. The verifier traced it: that keeps the sidecar's bookkeeping consistent, but does nothing to stop two physical workers running the same key's user code concurrently during a transient blip — the original worker is still alive and finishing while the redelivered copy starts elsewhere. Every host-side invariant reads green while the one guarantee the product is sold on is violated in reality.
Status A live correctness gap in a requirement currently treated as decided. This is not a preference — it should be escalated regardless of which other ideas are adopted.
2

One connection, fan-out inside the client (the admin model)

work hand-outConfidence: HighComplexity: MSETTLED

The protocol permits exactly one connection per application. An admin holds the stream and relays to its workers — a goroutine talking to worker goroutines in Go, a process talking to worker processes in Python. Identical shape in both languages, so the client translates with far less error surface, and the sidecar never learns whether the far end is threads or processes.

Basis
external: Beam's SDK harness does exactly this — one harness fans out internally, threads for Java/Go and one subprocess per core for Python because of the GIL, muxed by instruction ID. Same GIL problem, solved without any multi-connection protocol. Correction retained from the verifier: Beam actually uses several distinct gRPC services per harness (control, data, state, logging), not literally one connection — the surviving idea is "one harness, internal fan-out", not "one socket".
Why it matters Every piece of proxy state this project has fought — round-robin allocation, no-starvation guarantees, the "no other worker was lost in the same window" attribution clause — is a consequence of several connections. One connection deletes the seam rather than patching it.
Honest cost Fan-out bugs move inside the client, invisible to the sidecar, and get written twice — but in each language's native idiom (multiprocessing, worker goroutines), which is the cheapest thing to write twice.
Verifier verdict overruled
Marked "refuted" for contradicting the many-direct-connections decision — but that decision is downstream of the credit model this session rejected. Overruled: it contradicts a superseded premise, and it is the user's own proposal, independently matched by the closest prior art in existence.
3

An epoch per delivery — fencing borrowed from Kafka's own exactly-once model

client shapefailure & recoveryConfidence: HighComplexity: SSETTLED

Every dispatched record carries an epoch. A dead client is fenced and the epoch increments when the record is handed to another worker; a report naming a superseded epoch is discarded. The worker echoes the epoch back verbatim and keeps no request map, no callback table, no dedupe cache — the sidecar is the only party holding state.

Scope of the fence — state it plainly
Fences reports and Kafka-side effects: workers never produce directly, so output travels back through the engine and the sidecar produces behind one epoch check — which is what keeps exactly-once entirely on the JVM side, one producer, one transactional id. It does not fence a worker's external side effects (a database write, an HTTP call). No system fences those; the protocol should not imply otherwise.
Basis
direct: markAbandoned(deliveryCount) and isReturnForSupersededDelivery() already implement precisely this rule in-process — confirmed by the verifier by reading the file. The "capture the delivery at dispatch, never read it at return" discipline becomes structural when the token is literally the thing handed out. external: Court docket numbers — the parties keep no ledger; the number is printed on the paper they were handed, and a filing citing a closed matter is rejected at intake.
Why it matters A stateless client cannot have a state bug. It also reuses logic that was expensive to get right rather than re-deriving it per language — and "echo these bytes" is the one instruction an author writing from the spec alone cannot misread.
4

Dispatch a wave of independent shard-heads, report each record separately

work hand-outConfidence: HighComplexity: Mdirect + external

Send several records from different shards in one message for wire efficiency, but report each independently as it completes. Because a shard holds at most one in-flight record, a wave never contains two records of the same key — so there is nothing to serialize and no shared verdict to construct.

Basis
direct: The async path completes each work container independently — verifier-confirmed at the Vert.x hook and at the shard's one-per-shard break. external: Beam bundles many elements and discards the whole bundle if any element fails, having deliberately rejected per-item outcome tracking as not worth the complexity.
Why it matters This is a capability the closest prior art declined to build. It amortises wire cost without inheriting all-or-nothing retry, and it makes the client's job the same three steps in every language: unpack wave, dispatch, report per record.
5

The engine puppeteers; the client spawns — policy in the sidecar, mechanism in the client

lifecycle & supervisionConfidence: HighComplexity: MSETTLED

The user's app starts the sidecar. The sidecar decides how many executors and when, and says so in a message. The client library — already inside the user's process, holding the user's function — does the actual spawning with its own language's native mechanism. The engine never learns what the function is, or what a function even is; it just asks for executors.

Why this beats both of the options it replaces
Against client supervises the sidecar: the bind-race election disappears, because one app process starts one sidecar — there is nothing to elect. The detached process group disappears too; it only existed so the sidecar could outlive whichever worker won the race, and the app is now the parent that should own it. Against sidecar spawns the workers: the sidecar would have needed to know how to start the user's program, which is deploy-time configuration that fails late — and it could only spawn a command, forcing the user's function to be an importable name rather than a closure. Keeping the mechanism client-side dissolves both.
What it settles downstream
Config travels connect-time over the protocol, expressed in the user's own language — no config files, no environment variables, no shell. Generated stubs are not a translation layer. Max concurrency is set by the app, sent to the engine, and used as the in-flight ceiling — which is already exactly what maxConcurrency × batchSize means to an external engine, so no core change is needed for it. App shutdown shuts the sidecar down: drain in-flight work within the bounded timeout, commit, leave the group. The no-connection grace period is no longer needed at all — the app's death is the signal, rather than something to infer from zero connections.
Residuals
SIGKILL backstop — if the app is killed outright nothing runs, so the sidecar must watch its parent and exit on its own (closing pipe, or PR_SET_PDEATHSIG on Linux). Otherwise a JVM leaks while still holding group membership, and partitions do not rebalance until the session timeout. Python spawn-method — fork inherits the closure for free; spawn (default on macOS and Windows) re-imports and needs something picklable. An API-shape and documentation question, not an architectural one. Credentials over the wire — see the settled list below; this revises a requirement rather than violating it, but it has to be written down.
6

A liveness lease, explicitly not a processing deadline

backpressurefailure & recoveryConfidence: HighComplexity: Mdirect

Assume the worker may hang, loop forever, or never report. A lease is attached at dispatch and extended by heartbeats on the stream; on expiry the record is abandoned with attempt count unchanged. Poison detection reads the delivery count that already increments on every hand-out. A legitimately slow worker heartbeats and holds its record indefinitely; a dead one does not.

Basis
direct: Verifier confirmed there is no wall-clock processing deadline anywhere in this path — the slow-work threshold only warns, never abandons. That is deliberate: "a record stays in flight until your function returns; there is no clock" is PC's stated differentiator against Share Groups, whose acquisition-lock timeout genuinely is a processing clock.
Why it matters Folds crash, hang, infinite loop and worker bug into one host-side path needing zero worker cooperation — therefore zero per-language code. The distinction from a processing deadline is the whole game: build the wrong one and the product loses its differentiator.

Settled during this run

  • The wrapper is the layer; Java is the degenerate case. One client model, with the protobuf hop absent in Java rather than a second architecture.
  • The engine puppeteers, the client spawns. Policy in the sidecar, mechanism in the client — survivor 5.
  • Workers never produce to Kafka directly. Output travels back through the engine and the sidecar produces. This is what lets survivor 3's epoch check carry exactly-once on its own — one producer, one transactional id, one fence.
  • Configuration is code, delivered connect-time over the protocol. No config files, no environment variables, no shell. Lean on the target language's own tooling; generated stubs do not count as a translation layer.
  • Max concurrency keeps its existing meaning. Set by the app, sent to the engine, used as the in-flight ceiling — already what it means to ExternalEngine. Two earlier proposals to withdraw it were both wrong.
  • App shutdown shuts down the sidecar. Drain within the bounded timeout, commit, leave the group. Plus a parent-death backstop for SIGKILL.
  • Native shared library: dead end. See the rejection table. Superseded 2026-08-17 — re-opened on the user's explicit request; see the continuation.

The frame: the direct dialect is the sidecar minus the wire

The engine's transport boundary already exists and is already transport-free: DispatchSink.dispatch(Dispatch) / ProxyProcessor.report(Report) — verified this run by reading the source. The engine package imports no gRPC class; its javadoc says "the engine is built against this pair only - it never imports a transport class". A native binding is a second front-end onto that same pair, with the wire hop collapsed to a function call — the same frozen contract, minus gRPC. This extends run 1's "the wrapper is the layer" frame one level down.

One nuance the verifier insisted on: the seam is protobuf-typed, not protocol-free — Dispatch and Report are generated protobuf classes, so an FFI front-end still constructs real protobuf objects Java-side from the bytes crossing the C boundary. That is a cost idea 8 turns into the design.

The same layers appear on both sides; only the transport between wrapper and session core changes. A reader who ignores the picture loses nothing — it restates the frame above.

Grounding Context

Codebase (verified this run, with a fresh-context verifier pass over every survivor's citations):

  • DirectParallelConsumerClient proves the no-sidecar path for Java — bound straight to core, "no IPC, no serialization … no protocol anywhere beneath it", with bannedDependencies keeping protobuf and gRPC off its classpath. But it is synchronous: its own javadoc concedes "the asynchronous form buys nothing" because a core worker thread is held for the user function's full duration — which is exactly the wrong shape for an FFI boundary (see idea 9).
  • ProxyProcessor extends ExternalEngine; completion is the withheld-mailbox sentinel pattern, per record, so an external caller reporting later is the designed path. ExternalEngine.setupWorkerPool unconditionally forces pool size 1 — one dispatcher thread (a caveat idea 9 carries).

  • Nine non-JVM client modules exist with opt-in foreign-toolchain Maven builds (-Dpc.foreignClients); the conformance suite runs one scenario set against multiple bindings with CoreBinding as the control arm. No native or per-language CI lanes exist yet.
  • Build constraints: Jabel Java-17-source / Java-8-bytecode repo-wide; the Mutiny module is the precedent for a per-module Java-17 floor. Institutional defect class: checks that report success without running — every new lane must be shown red on a broken tree before its green counts.

7

Pull-only boundary — the engine never calls out

ffi boundaryConfidence: HighComplexity: Mexternal + direct

No Java→foreign function pointers exist anywhere in the ABI. The host language spawns its own workers in its own idiom — goroutines, Python threads, tokio tasks — and each one attaches (graal_attach_thread, idempotent) and calls in: pc_next() parks on the engine's wave queue; pc_report() completes a record. The engine's threads never cross the boundary outward. This inverts the assumption underneath the parked note's entire difficulty table, which rated languages by how hard it is for Java to call out into them.

Basis
external: oracle/graal#730 — callbacks into Java via function pointer from an unattached foreign thread are documented as not fully supported; the pull model makes the gap unreachable rather than worked-around. Same law in unrelated domains: SGX "switchless calls" (calls-out were the expensive fraught direction; the fix was host threads calling in and staying), CLAP/VST thread contracts (the host's threads enter the plugin; the plugin never invades the host), librdkafka's poll model. direct: the parked note's premise, quoted: "the engine must call out of native-image Java, on many threads at once, into the host runtime" — every "hard" rating downstream of it.
Why it matters — this re-ranks the languages A Python thread blocked in a C call releases the GIL for free — no PyGILState choreography; a blocking cgo call is idiomatic Go; a Node worker_thread pumps and posts to the loop. The languages the callback table ranked medium/hard are the languages where the market gap lives. The pull boundary also mirrors the existing client shape exactly — gRPC clients already pull dispatches off a stream — so client code structure is unchanged between dialects.
Verifier "Sound, and the strongest candidate here" — composes with the session core's existing async-sentinel wave queue rather than requiring new machinery.
8

The frozen protocol's frames are the C ABI

ffi boundaryConfidence: HighComplexity: Mdirect + external

The C surface is ~5 functions — create, next, report, metrics, close — and everything crossing it is a length-delimited ClientMessage/ProxyMessage, exactly the bytes the wire carries. Every language reuses its already-generated protobuf parser; the golden-bytes fixture becomes the ABI conformance fixture verbatim; buf breaking already gates ABI evolution; the capability list — the protocol's only versioning mechanism — versions the binding for free. The direct dialect simply never negotiates the tokens that only make sense across a process boundary.

Basis
direct: protocol-specification.md: golden bytes are "the cross-language fixed point"; the capability list is "the protocol's only versioning mechanism", and an empty list is legal v1. The token rule already fits an FFI: opaque, never parsed, "echoed byte-identically". external: librdkafka — pass-through content is why its bindings survive core evolution; DuckDB/SQLite — the success factor is a stable, tiny C surface; Arrow — what crosses is data only.
Why it matters It converts the first run's decisive rejection ground — "its failures are segfaults … where gRPC and protobuf fail legibly" — into a non-issue: a malformed message across this boundary fails as a protobuf parse error in the language's own exception system. It also collapses the marginal cost of a binding from "design and maintain an FFI object model" to "swap the transport under the existing client", and memory ownership becomes trivial: bytes are copied at the border, each side frees its own, no cross-heap references for two GCs to disagree about.
Honest cost, and the flagged experiment Per-record serialize/parse may eat exactly the win embedding promises for fast records. A zero-copy variant (Arrow-style record views into the isolate heap) was proposed and downgraded by the verifier — as stated it omits GC pinning (PinnedObject), without which the isolate's collector can move the bytes under the host's pointer. It survives only as an experimental arm of the crossover experiment (idea 10), not as the v1 boundary.
9

Bind at the session core, not the direct client

engine seamConfidence: HighComplexity: Mdirect

The FFI front-end is a second shell over ProxyProcessor/DispatchSink — the same session core the gRPC transport drives. pc_next drains the same wave assembler the stream reader drains; pc_report calls the same one-and-only completion path. Epoch fencing, leases, wave assembly, the produce-completion lane and returnToScheduling are reused verbatim, so the sidecar and the binding cannot drift semantically — there is one implementation of the semantics.

Basis
direct: DispatchSink javadoc: "The engine is built against this pair only - it never imports a transport class" — and zero io.grpc imports in the engine package, verified by grep this run. ProxyProcessor javadoc: report "later calls the container's success/failure hook and then addToMailbox - the one and only completion path, so ordering and retry are core's, untouched."
The alternative, rejected on its own javadoc Wrapping DirectParallelConsumerClient was proposed as the reuse-first path (fewest new lines on the segfault path). The verifier adjudicated against it: that client runs the user function synchronously on core's worker threads — its own javadoc says the async form "buys nothing" there — so an FFI wrap would hold a core thread hostage for every foreign call and cannot compose with the pull model at all. The DRY instinct behind the proposal survives in this idea; the attach point does not.
Caveat to carry into the experiment ExternalEngine pins the dispatch pool to one thread. The embedded path's headline win is therefore latency (real — the hop is gone); the throughput win is unproven until the crossover experiment separates dispatch-side single-threading from wire cost.
10

The probe ladder: qualification → Rust substrate → Python market

binding substrateConfidence: HighComplexity: Mdirect

Probe 0 — qualification. Re-fly the exact hand-out loop R25 cleared, compiled --shared, driven from a small C harness. Five pass/fail items, each demonstrated able to fail before its pass counts: entry-point surface; isolate/thread-attach; GC coexistence under host malloc pressure; foreign-thread callback re-entry (probed even though idea 7's design avoids it); and the single-artifact hypothesis — whether one build can serve as both the sidecar executable and the loadable library (GraalVM documents that --shared exposes a main entry point; whether that yields one dual-role artifact is unverified, and the verifier flagged it as a hypothesis, not a fact). Probe 1 — Rust. The invisible sidecar — vendor the executable that already cleared

binding substrateConfidence: HighComplexity: Sdirect + external

"No sidecar needed" may mean "no managed process", not "no second process". Each language package vendors the R25-cleared 45MB native executable as a package resource; the client library spawns it invisibly on first poll, supervises it via the already-designed parent-death pipe, and connects over loopback. The user never names, installs, deploys or operates a process — the API is indistinguishable from an embedded engine.

Basis
direct: parked note: "No process to operate, which is the single biggest adoption objection to the sidecar" — this answers that objection with zero new native-image risk; every gate this path needs is already cleared. R52: the proxy exits when its parent dies, including SIGKILL. external: puppeteer vendors Chromium; embedded-postgres vendors a database; Temporal's test server ships inside its SDKs.
Why it matters Shippable in weeks per language, retains the crash isolation that is the process boundary's one decisive win, and becomes the control arm every FFI binding must beat. If probe 0's single-artifact hypothesis holds, upgrading a deployment from invisible-sidecar to in-process later is a backend flag, not a migration — and if it does not hold, this path still stands on its own.
Meeting question — resolved 2026-08-17
The question was: is the complaint process existence or process management? The owner's answer: management — the goal was eliminating the gRPC hoops and reliability surface; performance is secondary. That resolution promotes this idea to the recommended first move: it delivers the operational simplicity that was the actual complaint at zero native-image risk, while the FFI path (ideas 7–9) stays gated behind the probe ladder (10) and must beat this as the control arm on the crossover number to justify idea 12's coexistence costs.
Stronger than resolved — this is the original intent, recovered. On walking through the mechanics, the owner confirmed the invisible sidecar is how they had always pictured the product being built — "I didn't know the words". The FFI reading of "native direct bindings, no sidecar" was an artifact of missing vocabulary, not the request. Idea 11 is therefore not a reframe of the ask; it is the ask, and the in-process path is the optimization track beyond it.
The reduced local dialect — invisible, and (almost) no heartbeat
The capability-token system already legalizes a leaner dialect for a supervised local child: the reconnect grace window and manifest exist for network blips, but over a local socket to a child you spawned, connection death ≈ process death — so the local dialect drops the reconnect machinery outright, and the parent-death pipe covers lifetime in both directions. What survives is the liveness lease against a hung worker — and its heartbeats were never user-facing: the client library sends them as internal plumbing. The user's experience is install, write a function, run.
Visible vs invisible — one product, two ways of finding the socket
The visible (explicitly deployed) sidecar is not a competing product but a supported mode: the library either spawns the vendored binary and connects (invisible, the default) or is handed an address and just connects (visible). Same binary, same protocol; the marginal cost of offering both is a constructor option, documentation, and a CI row — the Dapr precedent (platform-injected in Kubernetes, self-spawned in dev) and librdkafka's bundled-vs-system choice. What the visible mode is for is operational control, not correctness: its own container with its own resource limits, log stream, metrics target and security profile; fleet-wide engine patching without re-releasing language packages (the trade against invisible's pinned-version skew safety); process models the 1:1 spawn cannot serve (gunicorn-style prefork wants one shared per-pod sidecar, not eight invisible children = eight group members); and platforms that forbid executing a package-vendored binary (read-only/noexec filesystems, distroless images). Language fit tracks deployment culture more than language: Python/Node/Ruby/.NET are invisible-natural (their package managers already ship fat native artifacts); Go and Rust are mixed (single-static-binary culture resists a 45MB vendored helper, and those communities run the platforms where a visible sidecar container is unremarkable); edge and embedded targets fit neither mode — which is the cleanest statement of what the FFI track (ideas 7–9) is actually for. Dialects differ per mode and the capability tokens carry it: invisible runs the reduced local dialect; a visible sidecar in a separate container can restart independently of the app, so the reconnect grace window and manifest earn their place there. Same frozen protocol, different negotiated capabilities.

The coexistence contract — what dies with the boundary, what it reveals, what v1 must expose

runtime coexistenceConfidence: MedComplexity: Mdirect + reasoned

Removing the process boundary deletes a whole chromosome of two-process survival machinery — the parent-death pipe, connection-loss grace window and manifest reconnect, heartbeat-extended leases, WorkerDied — every one a solution to "the other process died / the pipe broke", which can no longer occur. Enumerate that as a design artifact (large negative scope), then write down what removal reveals rather than discovers in production:

  • A hung foreign thread silently holding a record forever — the lease survives, scoped to a thread instead of a connection.
  • Shutdown — fate is shared, so drain must be hooked into the host's exit path per language (a Go os.Exit skips defers; an atexit story is part of the binding's contract).
  • Engine restart without process management — graal_tear_down_isolate plus a fresh isolate, with the already-specified manifest-reconnect protocol reused verbatim as the recovery story; only a hard segfault still takes the host.
  • Memory — the isolate heap is invisible to the host's tooling, so the max-heap is a required field at create time (config-is-code extended to creation), and engine metrics plus isolate heap stats export through the host language's own registry. Signal handlers built out.
  • fork() — Python's default deployment shape preforks; an isolate's threads do not survive fork. pthread_atfork poisons the child handle to a legible error (librdkafka's documented fork-unsafety is the precedent — verified independently this run), and the conformance lane tests it.
Basis
direct: the R52/KTD19 pipe, R46 lease and R42/43 manifest wording all verified in the plan; PCMetrics gauges already exist at the right layer. external: isolate heap "no shared visibility" and signal-handler guidance per GraalVM docs; endosymbiosis as the structural analogy — organelles shed the genes whose problems the host now owns. reasoned: in-process, worker liveness and engine liveness are the same event except for hangs — which is why the lease survives when everything around it goes extinct.
Why it matters These are the failure modes that surface six months post-GA as unreproducible hangs and container OOM kills. Every one is cheap as API design now and expensive as retrofit — and the enumeration itself is mostly negative scope, the cheapest kind to settle.

Cold-chain packaging — decouple the lib from nine thin packages, and build the fail-closed lane first

packaging & ciConfidence: MedComplexity: Mdirect + external

Ship libparallelconsumer as a per-platform artifact family (the netty-tcnative classifier pattern, ~5 platforms), and make the nine language packages thin: they pin a minimum lib version and locate it — bundled like confluent-kafka-python's wheels, or system-resolved like librdkafka — rather than compiling it in. A Kafka bump then re-releases the lib family while zero language packages change (the frames-as-ABI choice in idea 8 is what makes that possible). Build the CI lane before the binding: every language lane runs the golden-bytes session through the FFI, pc_build_info() echoes the git SHA so a stale or stubbed lib fails loudly, and each lane is demonstrated red on a deliberately broken tree before its green is trusted.

Basis
direct: the parked note's decisive cost, quoted: "a version bump goes from a dependency change to a rebuild and re-release of every platform binary and every language package that vendors one" — this idea is aimed squarely at that sentence. Evidence pass: no native or per-language CI lanes exist today; the repo's most recurrent tooling defect is checks that report success without running. external: netty-tcnative per-platform classifier jars; confluent-kafka-python bundled-vs-system librdkafka.
Why it matters If the matrix lane exists, is fail-closed and is push-button, the parked note's strongest recorded cost collapses from an architecture-level currency penalty to CI minutes — which changes the embedded-engine decision itself. The lane also de-risks ideas 10 and 11, which need the identical matrix.
