Part 1 · Interaction Model

2026-08-14 · 27 raw candidates → 16 after merge → 6 survivors: 3 settled, 3 open · 5 axes · repo-grounded

The subject is how the sidecar and its non-Java workers interact — not the transport (gRPC is settled) and not the product scope. The credit-ledger design was rejected before this run began; the question is what replaces it, and how much of the client library survives that choice.

The frame: the wrapper is the layer

"PC in every language" means every language gets the same client wrapper, and to the user it looks native. Java's wrapper is that same layer with one fewer hop — it sits directly on the engine with no protobuf underneath. This is one client model with a missing layer in the Java case, not two architectures, and every idea below is judged against that frame.

Read this first: the verifier was judging a stale document

The fresh-context verifier scored every candidate against docs/plans/2026-08-12-001-feat-language-proxy-plan.md, which still carries the credit model (KD9, KTD9, R23) and its dependents (KD8's many-direct-connections, KTD9's round-robin allocator) as settled. Several "refuted" verdicts rest entirely on contradicting decisions this session has already superseded.

Those verdicts are overruled below, each with its reason stated. Verdicts resting on code or on prior-art accuracy are retained — and two of them materially downgraded ideas I was enthusiastic about.

Grounding Context

Codebase (verified this run, with a second pass by the verifier):

  • ExternalEngine forces the worker pool to size 1 — external engines do not use a thread pool; one thread dispatches. Vert.x and Reactor already ride this seam.
  • getTargetAmountOfRecordsInFlight() == getMaxConcurrency() * getBatchSize(), and ExternalEngine.getTargetOutForProcessing() returns exactly that — so max concurrency is already how the existing external engines bound in-flight work, not a thread-pool size.
  • calculateQuantityToRequest() computes target − numberRecordsOutForProcessing every control-loop pass, so an engine can vary its target dynamically.
  • On the async path, ExternalEngine withholds the mailbox entry so each WorkContainer completes independently. Per-record outcomes from a batch are therefore possible — the old plan's claim to the contrary does not hold on this path.
  • ProcessingShard permits at most one in-flight record per shard under restricted ordering. Key ordering is enforced host-side, for free.
  • WorkContainer.markAbandoned(deliveryCount) + isReturnForSupersededDelivery() already implement verdict-free return and late-duplicate rejection, in-process.
  • Verifier addition: WorkManager.numberRecordsOutForProcessing is a live accumulator with five mutation sites, and the silent-stall learning attributes a real bug to drift in exactly that counter.

External prior art — Apache Beam's Fn API (runner owns scheduling, per-language SDK harness runs user code, gRPC between them; Python fans out to one subprocess per core for the GIL; bundles retry whole, per-item outcomes deliberately rejected) · Temporal (shared Rust sdk-core with thin bindings; workers poll; host-side "slots") · Ray (node-local daemon owns worker lifecycle; language driver never spawns) · Envoy ext_proc (stream per request; processor controls granularity) · Bytewax (Rust core, Python in-process FFI, no IPC) · Dask (batch assignment to least-busy worker).

Standing constraint: four consecutive review rounds on the flow-control / in-flight-accounting seam each produced the next round's defect. The recorded instruction is to change a decision rather than patch that seam again — which is what this whole exercise is.

Ranked Ideas

1

Reconnect reconciles a manifest — a dropped pipe is not a dead worker

failure & recoveryConfidence: HighComplexity: Mexternal + direct

Connection loss does not immediately abandon that connection's records. The sidecar protects them for a bounded grace window; the reconnecting client opens with a manifest of tokens its live workers still hold; the sidecar reconciles — still-current tokens stay in flight untouched, superseded ones are ordered dropped, absent ones are abandoned with attempt count unchanged. Only window expiry abandons.

Basis
external: ATC lost-communications procedure — losing radio contact does not mean losing the aircraft. The controller protects the clearance rather than reassigning the level; reassigning on contact loss is the accident-causing move. direct: A TCP drop is information about the pipe, not the executor.
Why it matters — this is the run's most valuable finding The current requirement says a closed connection returns that worker's records immediately. The verifier traced it: that keeps the sidecar's bookkeeping consistent, but does nothing to stop two physical workers running the same key's user code concurrently during a transient blip — the original worker is still alive and finishing while the redelivered copy starts elsewhere. Every host-side invariant reads green while the one guarantee the product is sold on is violated in reality.
Status A live correctness gap in a requirement currently treated as decided. This is not a preference — it should be escalated regardless of which other ideas are adopted.
2

One connection, fan-out inside the client (the admin model)

work hand-outConfidence: HighComplexity: MSETTLED

The protocol permits exactly one connection per application. An admin holds the stream and relays to its workers — a goroutine talking to worker goroutines in Go, a process talking to worker processes in Python. Identical shape in both languages, so the client translates with far less error surface, and the sidecar never learns whether the far end is threads or processes.

Basis
external: Beam's SDK harness does exactly this — one harness fans out internally, threads for Java/Go and one subprocess per core for Python because of the GIL, muxed by instruction ID. Same GIL problem, solved without any multi-connection protocol. Correction retained from the verifier: Beam actually uses several distinct gRPC services per harness (control, data, state, logging), not literally one connection — the surviving idea is "one harness, internal fan-out", not "one socket".
Why it matters Every piece of proxy state this project has fought — round-robin allocation, no-starvation guarantees, the "no other worker was lost in the same window" attribution clause — is a consequence of several connections. One connection deletes the seam rather than patching it.
Honest cost Fan-out bugs move inside the client, invisible to the sidecar, and get written twice — but in each language's native idiom (multiprocessing, worker goroutines), which is the cheapest thing to write twice.
Verifier verdict overruled
Marked "refuted" for contradicting the many-direct-connections decision — but that decision is downstream of the credit model this session rejected. Overruled: it contradicts a superseded premise, and it is the user's own proposal, independently matched by the closest prior art in existence.
3

An epoch per delivery — fencing borrowed from Kafka's own exactly-once model

client shapefailure & recoveryConfidence: HighComplexity: SSETTLED

Every dispatched record carries an epoch. A dead client is fenced and the epoch increments when the record is handed to another worker; a report naming a superseded epoch is discarded. The worker echoes the epoch back verbatim and keeps no request map, no callback table, no dedupe cache — the sidecar is the only party holding state.

Scope of the fence — state it plainly
Fences reports and Kafka-side effects: workers never produce directly, so output travels back through the engine and the sidecar produces behind one epoch check — which is what keeps exactly-once entirely on the JVM side, one producer, one transactional id. It does not fence a worker's external side effects (a database write, an HTTP call). No system fences those; the protocol should not imply otherwise.
Basis
direct: markAbandoned(deliveryCount) and isReturnForSupersededDelivery() already implement precisely this rule in-process — confirmed by the verifier by reading the file. The "capture the delivery at dispatch, never read it at return" discipline becomes structural when the token is literally the thing handed out. external: Court docket numbers — the parties keep no ledger; the number is printed on the paper they were handed, and a filing citing a closed matter is rejected at intake.
Why it matters A stateless client cannot have a state bug. It also reuses logic that was expensive to get right rather than re-deriving it per language — and "echo these bytes" is the one instruction an author writing from the spec alone cannot misread.
4

Dispatch a wave of independent shard-heads, report each record separately

work hand-outConfidence: HighComplexity: Mdirect + external

Send several records from different shards in one message for wire efficiency, but report each independently as it completes. Because a shard holds at most one in-flight record, a wave never contains two records of the same key — so there is nothing to serialize and no shared verdict to construct.

Basis
direct: The async path completes each work container independently — verifier-confirmed at the Vert.x hook and at the shard's one-per-shard break. external: Beam bundles many elements and discards the whole bundle if any element fails, having deliberately rejected per-item outcome tracking as not worth the complexity.
Why it matters This is a capability the closest prior art declined to build. It amortises wire cost without inheriting all-or-nothing retry, and it makes the client's job the same three steps in every language: unpack wave, dispatch, report per record.
5

The engine puppeteers; the client spawns — policy in the sidecar, mechanism in the client

lifecycle & supervisionConfidence: HighComplexity: MSETTLED

The user's app starts the sidecar. The sidecar decides how many executors and when, and says so in a message. The client library — already inside the user's process, holding the user's function — does the actual spawning with its own language's native mechanism. The engine never learns what the function is, or what a function even is; it just asks for executors.

Why this beats both of the options it replaces
Against client supervises the sidecar: the bind-race election disappears, because one app process starts one sidecar — there is nothing to elect. The detached process group disappears too; it only existed so the sidecar could outlive whichever worker won the race, and the app is now the parent that should own it. Against sidecar spawns the workers: the sidecar would have needed to know how to start the user's program, which is deploy-time configuration that fails late — and it could only spawn a command, forcing the user's function to be an importable name rather than a closure. Keeping the mechanism client-side dissolves both.
What it settles downstream
Config travels connect-time over the protocol, expressed in the user's own language — no config files, no environment variables, no shell. Generated stubs are not a translation layer. Max concurrency is set by the app, sent to the engine, and used as the in-flight ceiling — which is already exactly what maxConcurrency × batchSize means to an external engine, so no core change is needed for it. App shutdown shuts the sidecar down: drain in-flight work within the bounded timeout, commit, leave the group. The no-connection grace period is no longer needed at all — the app's death is the signal, rather than something to infer from zero connections.
Residuals
SIGKILL backstop — if the app is killed outright nothing runs, so the sidecar must watch its parent and exit on its own (closing pipe, or PR_SET_PDEATHSIG on Linux). Otherwise a JVM leaks while still holding group membership, and partitions do not rebalance until the session timeout. Python spawn-method — fork inherits the closure for free; spawn (default on macOS and Windows) re-imports and needs something picklable. An API-shape and documentation question, not an architectural one. Credentials over the wire — see the settled list below; this revises a requirement rather than violating it, but it has to be written down.
6

A liveness lease, explicitly not a processing deadline

backpressurefailure & recoveryConfidence: HighComplexity: Mdirect

Assume the worker may hang, loop forever, or never report. A lease is attached at dispatch and extended by heartbeats on the stream; on expiry the record is abandoned with attempt count unchanged. Poison detection reads the delivery count that already increments on every hand-out. A legitimately slow worker heartbeats and holds its record indefinitely; a dead one does not.

Basis
direct: Verifier confirmed there is no wall-clock processing deadline anywhere in this path — the slow-work threshold only warns, never abandons. That is deliberate: "a record stays in flight until your function returns; there is no clock" is PC's stated differentiator against Share Groups, whose acquisition-lock timeout genuinely is a processing clock.
Why it matters Folds crash, hang, infinite loop and worker bug into one host-side path needing zero worker cooperation — therefore zero per-language code. The distinction from a processing deadline is the whole game: build the wrong one and the product loses its differentiator.

Settled during this run

  • The wrapper is the layer; Java is the degenerate case. One client model, with the protobuf hop absent in Java rather than a second architecture.
  • The engine puppeteers, the client spawns. Policy in the sidecar, mechanism in the client — survivor 5.
  • Workers never produce to Kafka directly. Output travels back through the engine and the sidecar produces. This is what lets survivor 3's epoch check carry exactly-once on its own — one producer, one transactional id, one fence.
  • Configuration is code, delivered connect-time over the protocol. No config files, no environment variables, no shell. Lean on the target language's own tooling; generated stubs do not count as a translation layer.
  • Max concurrency keeps its existing meaning. Set by the app, sent to the engine, used as the in-flight ceiling — already what it means to ExternalEngine. Two earlier proposals to withdraw it were both wrong.
  • App shutdown shuts down the sidecar. Drain within the bounded timeout, commit, leave the group. Plus a parent-death backstop for SIGKILL.
  • Native shared library: dead end. See the rejection table.

What this set does not settle

  • Survivors 1, 4 and 6 remain open. The reconnect manifest (survivor 1) is the one that should be treated as a defect rather than a choice — it is a correctness gap in a requirement currently treated as decided, and it needs fixing whichever way the rest goes.   • Swift. Raised as a target during this run. Under the wrapper frame it is another client rather than a new architecture — useful mainly as a stress test: if adding it is cheap, the shape is right.

The skateboard stack: conformance runners in demo costume, receipts over the produce path, one TUI, a recorded cast

proving samenessaggregation & uidistributionConfidence: 85%Complexity: Medium
Description

Four existing assets compose into the end-to-end demo with almost no new code. (1) Each language's demo is its conformance runner wearing a costume — the runner already connects over production gRPC and prints the frozen observation line per delivery; the demo is that binary with a real-sidecar flag plus the R77 stats printer. (2) Each worker's Success report carries a receipt — {record_id, language, offset, attempt, payload_checksum} — produced through the protocol's only sanctioned output route onto a demo-observations topic, so Kafka itself is the aggregation bus: no log-shipping fabric, and the demo's plumbing dogfoods terminal produce and the epoch fence. (3) The single UI is a small TUI aggregator container — one plain consumer of the receipts topic rendering eleven lanes — that also machine-asserts sameness: matching checksums per record and one line at the end, "11/11 languages converged at offset N". (4) CI records the run as an asciinema cast into the README's existing demo slot, refreshed each release — a broken demo breaks the reel, so distribution doubles as a continuous end-to-end test. Design the receipt/stats seam as a clean interface so the parked web-GUI dashboard can slot in later as a dependency, not a rewrite.

Illustrative — the direction's shape, not a spec.
Basis
direct: conformance README — "dispatch key=<key> offset=<n> attempt=<n> reason=<last-failure-reason>", "Anything else on stdout is ignored", and "adding a language is one runner and one registry entry. There is no test to port." direct: protocol spec — Report.Success "may carry produce… the only sanctioned route for worker output to Kafka"; verifier-confirmed in proxy.proto, arbitrary topic legal in frozen v1. direct: src/docs/README_TEMPLATE.adoc demo section already embeds an asciinema player; the parked gallery's own fallback ladder ends in "recorded captures". external: Dapr Multi-App Run — one command, N language apps — is the UX precedent; Temporal Polyglot's missing unified view is the gap.
Rationale

This is the user's ask delivered as a skateboard: every layer reuses something already built, already tested, or already frozen — so the first shippable version is mostly wiring. The receipts move makes the proof machine-checked (checksums, convergence) instead of eyeballed logs, answers "collecting logs together" with the product's own produce path, and exercises the one protocol feature no demo would otherwise show. Recording it closes distribution without touching either parked effort.

Downsides

A TUI is less shareable as a live artifact than a web page (mitigated by the cast); receipts add produce load to the demo workload — negligible at demo rates, but a constraint from the perf track: when an arm is under measurement, the harness must be able to run with receipts off, or the receipts' produce cost must appear as its own component in the attribution ladder — the demo's transport must never distort the numbers it displays. The runner-in-costume framing must not leak conformance-only flags into the user-facing demo UX, or KTD40's identical-UX contract gets muddied.

2

The two-act show with a chaos finale: one consumer group across eleven runtimes

proving samenessConfidence: 80%Complexity: Medium–Large
Description

"They all read the same records" is ambiguous, and the demo should exploit that instead of picking silently. Act 1 — everyone reads everything: eleven consumer groups, one topic; every language processes every record; identical behaviour side by side (optionally rendered record-centric — one "speaker" feed, eleven booth renderings, UN-interpreting style — rather than eleven independent lanes). Act 2 — one team shares the work: all eleven join one consumer group and cooperatively split the topic. Render the offset axis as a Jepsen-style colour plot — each record coloured by the language that processed it — then pull the andon cord: SIGSTOP a lane and its partitions' colours freeze while ten advance; SIGKILL it and the broker's own rebalance hands its partitions to a demo written in a different language, records redelivering with attempt=2 and the failure reason carried verbatim. The proof is the broker's coordinator and the engine's redelivery semantics — facts the demo cannot fake — not the demo's own logging.

Illustrative — the direction's shape, not a spec.
Basis
direct: Part 1's settled model — "the protocol permits exactly one connection per application" with one sidecar per app — plus the plan's statement that the Kafka cluster "sees an ordinary consumer group member": eleven apps in one group are just eleven ordinary members. Verifier note: sound as architecture, but inferred — no requirement writes the shared-group demo down, so this is a genuine design decision. direct: conformance scenario "a-failed-record-is-redelivered-with-its-failure-history" asserts the reason is carried verbatim; the chaos scenario framework already exists on feats/web-gui, and docs/inflight/branch-language-proxy.md names it as something "this work would want". external: Jepsen op-colour-plots — consistency made visually legible.
Rationale

Happy-path sameness is weak evidence — eleven green lanes could all be faking it, which is the conformance suite's own founding argument. Cooperative rebalancing across eleven runtimes through one engine implementation is the strongest possible claim of behavioural identity, and the colour plot is the shareable screenshot no other vendor has. The kill beat converts an already-tested protocol behaviour into the demo's most convincing thirty seconds, for free.

Downsides

Act 2 needs partitions ≥ languages and a workload shaped so every language visibly participates; the chaos framework lives on a sibling branch (consume it as a dependency when it lands, or ship a demo-local kill script until then); a two-act script is more demo choreography to maintain than a single always-on view.

3

The demo is conformance infrastructure: golden transcript, generated compose, one launch path, go/no-go roll call

orchestrationper-language clientsConfidence: 85%Complexity: Medium
Description

Treat the demo layer with the same discipline the wire already gets, four moves. (1) Golden demo transcript: normalise the reference demo's output (strip timestamps and the language tag) and CI-diff every language's demo against it byte-for-shape — KTD40's seven rules become a machine check, not eleven authors hand-mirroring a document; the party trick on top is "lineup mode" (lanes labelled A–K, audience challenged to spot Ruby — they can't). (2) Generated orchestration: emit the compose services from the conformance suite's LanguageRunners registry so there is never a second hand-maintained list of eleven languages — a twelfth language appears in the demo by adding its registry entry. (3) One launch path: run.sh is the CI cross-language integration test (--ci flag), and demo images ride the existing bin/build-client.sh gate and KTD35 checkpoints — the demo cannot silently rot because CI runs it. (4) Go/no-go roll call: the workload fires only after all requested lanes report GO (connected, handshake, self-check) with per-lane reasons on NO-GO — a silently absent lane must never read as a green wall. Default to a fast subset; --languages=all opts into the full eleven.

Basis
direct: conformance README — "Ten definitions of correct is no definition at all… Written once, agreement between clients is evidence; written eleven times, it is coincidence", and "Absence must never read as agreement". direct: plan — KTD40's own risk note: "the mode logic is the part that will drift, because eleven authors each have a reasonable opinion about it"; U16 lists run.sh, docker-compose.yml and CrossLanguageConcurrencyIT.java as one unit's fileset; KTD25 "a matrix keyed on language… adds a language by adding a row"; bin/build-client.sh — "a red test… fails the IMAGE BUILD, which fails the Maven reactor". direct: R20's singular wording confirms the eleven-at-once launch is unspecified — the subset-default question is genuinely open. external: gRPC's interop matrix — conformance as a language-cross-version grid.
Rationale

The most likely failure of this whole feature is not building it — it is the demo being subtly different in three languages and broken in two more six months later, discovered live in front of an audience. Every mechanism here already exists for the protocol layer; extending the same epistemology (golden fixed points, single source of truth, absence-fails-loud) down to the demo layer is cheap now and unaffordable to retrofit.

Downsides

Transcript normalisation needs care (timestamps, rates, locale) or the diff flakes; generating compose from a Java registry needs a small extraction step at build time; the roll-call barrier adds startup latency to the full-eleven mode (acceptable — it replaces a race).

The live performance show: single-clock scoreboard, streaming plots, and the story page

aggregation & uidistributionConfidence: 80%Complexity: Medium–Large
Description

Don't just publish the performance numbers — run the performance test live inside the demo and let the audience watch the evidence accumulate. A web dashboard plots results as they arrive: each measurement lands as a point, the percentile bands tighten on screen, and the chart builds rather than appears — the reproducibility argument made visible. Structure it as the two-shapes story the benchmark design already mandates: the realistic key-ordered scenario this product exists for, and the plain unfavourable case published on purpose — honesty as the narrative arc. Three layers share one measurement seam:

  • Photo-finish timing: the sidecar — one JVM, one clock — timestamps dispatch-out and report-in for every language: honest per-language p50/p99 with zero cross-container clock skew, in-process Java as the printed pace car (the Java client's two transports make the hop cost a visible delta on otherwise-identical code). Ban per-container clocks from the board.
  • Live web dashboard: a small results-plotting page (streaming points over WebSocket or polling the receipts topic) — each language's curve drawing itself during the run, displayed as the attribution ladder (java-direct → java-gRPC → foreign client: engine cost + protocol cost + runtime cost as stacked components) and as per-language ratios against the in-process Java baseline — never an absolute records/sec ranking. Hardware class printed on screen; the honest run shape is mock-mode all-parallel (labelled) or a carousel spotlight — one language measured on the uncontended broker while the others tick — because thirteen concurrent workloads starving one broker is noise, not data. A results surface, deliberately distinct from the parked engine-internals dashboard; a Prometheus + Grafana fragment remains the ops-shaped variant.
  • The story page: the static marketing/method page rendered not from the live run but from the blessed-numbers pipeline — docs/data/performance-profile.d/ fragments validated by the existing docs-data gate — with the method beside the numbers, the expected-loss case stated plainly, effective-config fingerprint printed (proxy UNSPECIFIED defaults diverge from core defaults, so parity must be pinned, not assumed), and links into the features corpus and testing-evidence entries. Embeddable in the README today, the docs site when astubbs#208 lands; local-first — a hosted live variant re-inherits every blocker that parked the gallery.
Illustrative — the direction's shape, not a spec.
Basis
direct: plan R31 — "v1 measures median and p99 poll-to-completion latency through the proxy and for in-process PC on the same workload, and reports both"; KTD20 — "One Java client API, two transports, one transport-parameterised test suite". direct: owner's recorded requirements in docs/inflight/parked-testing-as-a-feature-for-the-clients.md (2026-08-15) — "the answer has to be visible, not asserted"; compare each language against the standard Java client, "not languages against each other"; reuse the two-shapes benchmark design from feats/ks-streams-seam-on-upstream-gate including "figures from a single run are not yet evidence". direct: PCMetricsDef's gauge/counter/timer set and the proxy constructing its own meter registry; verifier-settled: R10 blocks passing the registry object over the wire, not a proxy-local scrape endpoint. direct: STRATEGY.md — "visibility is the bill that comes with the choice". reasoned: the single-clock argument: all timing already flows through one process, so the demo gets honest cross-language comparison structurally, where per-container timestamping would be junk — and a chart that visibly accumulates samples is the single-run caveat answered on screen.
Rationale

"What does the hop cost in my language?" is the first question every evaluator asks, and the easiest to measure wrongly. Running the required R31 measurement live — plots forming as results arrive, the unfavourable case shown on purpose — turns the benchmark from a table someone must trust into a process the viewer watched, which is the "visible, not asserted" requirement taken to its logical end. The story page then reuses the same output as the release's most persuasive artifact, with the docs-gate keeping its claims from quietly going stale.

Downsides

Framing constraint is hard: the recorded owner rule is per-language-vs-Java hop cost, never a cross-language race — the dashboard must not render as a language leaderboard. Live numbers on demo hardware are demonstrations, not published benchmarks — the story page must carry the method and the reproducibility caveats or it becomes the badly-run benchmark the parked notes warn about. A results web page is a second web surface near the parked engine-internals dashboard — keep the seam shared and the pitch distinct, or fold them when feats/web-gui lands. Measurement design (scenarios, harness, credibility) is in flight in a concurrent session — this idea owns presentation and must consume that session's results format, not fork its own.
