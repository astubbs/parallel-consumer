A Dapr Adapter for Parallel Consumer

Date 2026-08-17 Topic dapr-adapter Mode repo-grounded Focus "look into making a dapr adapter — search existing PRs for prior art"

Grounding Context

Prior-art search result: no PR or issue in either astubbs/parallel-consumer or upstream confluentinc/parallel-consumer mentions "dapr" — verified across all states, titles and bodies. The real prior art lives in this repo's own git history: astubbs#242 (mirror of confluentinc#154, "Integrate into a Proxy") and three inflight docs captured 2026-08-15 at commit 85cfce876 — next-study-dapr-and-kafka-proxies.md (the Dapr study), next-http-strategy-ideas.md (§3 names the Dapr adapter "the highest-leverage" integration, with two unknowns: contract expressiveness, and the two-sidecars deployment smell), and next-work-server-pitch-and-buyer.md (the shared-interface architecture and buyer analysis).

Codebase state: a proxy sidecar module exists on branch feats/proxy-requirements — ProxyProcessor wraps the core engine as an ExternalEngine; a frozen gRPC v1 protocol carries per-record tokens (topic/partition/offset + delivery epoch + attempt metadata) with epoch fencing of dispatch and report; the engine seam (DispatchSink) imports no transport class. Integration precedent: streams/connect previews ship as isolated opt-in alpha modules.

External research (high value): Dapr's pluggable pub/sub contract (pubsub.proto, PullMessages) is a bidirectional gRPC stream where daprd acks per message, independently, not necessarily in delivery order — structurally the same shape as PC's Dispatch/Report cycle. Dapr's built-in Kafka component has documented head-of-line-blocking complaints (dapr#5946). No third-party Dapr component offers ordering-preserving concurrency. KIP-932 share groups are GA (Kafka 4.2.0, 2026-02-17), giving Kafka native unordered concurrent consumption — PC's durable differentiator narrows to order-preserving concurrency. Dapr graduated CNCF (2024-10); pluggable components sit outside its certification lifecycle and have no registry (dapr#5210).

Topic Axes

What a Dapr Adapter Unlocks

A new user base, not a feature for the existing one. PC today is adoptable only by JVM teams programming against a Java library. Dapr's users are the opposite population: polyglot microservice teams (Go, Python, .NET, JS…) on Kubernetes who deliberately don't want to know broker details. One component reaches every Dapr-supported language at once — "one component, not eleven libraries" — a population the current distribution model structurally excludes.

A real, documented pain removed for them. Dapr's built-in Kafka component is partition-bounded and processes sequentially per partition; Dapr's own users complain about it (dapr#5946). A PC-backed component removes that ceiling with no change to their programming model. Dapr solves coupling, PC solves concurrency — the adapter multiplies the axes rather than competing, so nothing is cannibalized and nothing has to be abandoned to adopt it.

Why now. The value of lifting the partition ceiling scales with how slow the work is, and inference-era workloads got slower — Dapr's growth area is AI workloads: slow, per-item, often key-ordered. Meanwhile KIP-932 sharpens rather than undercuts the case: Kafka natively answers "concurrency, order be damned," leaving ordered concurrency as the empty quadrant — and the Dapr component catalogue is where that gap is most legible to buyers.

Strategic side-payoffs for PC: a route to the platform-team buyer at sidecar cost (Component YAML + secret store + app scoping — config governance, though not the operational burden, of the server shape); empirical demand data ordering the eleven-client backlog; and a five-minute cross-language demo path that "adopt our Java library" can never be.

Honest limits: consume-transform-produce loses produce-then-complete atomicity (those users stay on the native proxy); discovery is informal (no component registry); and the unlock is conditional on daprd's delivery concurrency — see idea 1, including the patch-upstream option.

Idea 1

The break-of-gauge probe: measure Dapr's semantics before building anything

contract-mapping
Description
Build a throwaway pluggable pub/sub component whose only job is to measure the four Dapr semantics every design decision hinges on: (a) is an ack emitted at app-completion or at daprd-receipt; (b) does daprd buffer between component and app — a hidden "capacitor" that would make PC's in-flight ceiling count records the app has never seen, and fire lease deadlines on them; (c) can the component distinguish app-death from daprd-death from stream-break; (d) what does daprd do after ack_error (redeliver? when? how often?). Output is a one-page semantics datasheet plus a reusable "work-shaped vs message-shaped" contract checklist that applies unchanged to the kafka-pixy and REST-Proxy compatibility questions later. The probe's verdict is a three-way triage, not a binary: (i) delivery is already concurrent → build as-is (plausible — dapr#5946 concerns the built-in Kafka component's per-partition goroutine model, which a pluggable component replaces entirely, and the app-max-concurrency annotation's existence implies concurrent delivery exists somewhere in the stack); (ii) daprd serializes → build the adapter and patch daprd upstream — Dapr is CNCF open source, the fix closes their own users' open complaint and benefits every component, and a visible upstream contribution is itself distribution in a registry-less ecosystem. This repo already has the discipline for exactly this situation: the Kafka Streams work patches upstream's published sources with a small tracked .patch applied at build time — reviewable, re-derivable, empty-patch control arm, no vendoring and no fork to maintain (docs/solutions/architecture-patterns/patch-a-dependency-at-build-time-without-vendoring-it.md, shipped in astubbs#271 / issue astubbs#255; mechanics in parallel-consumer-streams/bin/apply-patch.sh on feats/ks-on-pc-spike). Applied to daprd: pin the upstream source, carry the tracked patch in the component's image build while the upstream PR bakes, drop the patch when it releases — which shrinks the "requires daprd ≥ X" version-gate window to near zero for users of our image; (iii) something structural and unpatchable → no-go, documented cheaply. The probe's second job is therefore locating any serialization (daprd core vs app channel vs language-SDK handler), since that determines what a patch touches. Nineteenth-century railways learned that joining two networks fails not at the visible interface (track gauge) but at the secondary ones — brakes, couplings — so junctions built verification rigs before through-running.
Why the paper analysis is encouraging but not sufficient
On paper, Dapr's contract is more compatible than the inflight docs feared: PullMessages already acks per message, out of order, and per-key ordering plus the in-flight ceiling are admission-side — PC's own v1 protocol states "flow control does not exist on the wire, deliberately", and ProcessingShard holds back same-key successors inside the engine. Nothing about ordering ever needs to appear on Dapr's wire. But the verifier correctly flagged the residual unknown as real: dapr#5946 suggests daprd→app delivery may serialize, which would recreate head-of-line blocking one hop downstream and void the benefit. That question is answerable only by measurement.
Basis
direct: "Both are speculation until someone reads their actual contracts. That reading is the task, not the integration." (next-study-dapr-and-kafka-proxies.md); "Flow control does not exist on the wire, deliberately" (proxy protocol spec). external: Dapr pubsub.proto PullMessages per-message ack; dapr#5946.
Rationale
The cheapest possible action (a probe) gates the most expensive possible mistake (building an adapter on a contract that turns out to be message-shaped). It converts the inflight docs' own stated task — "read their contracts" — into falsifiable pass/fail measurements, and upgrades reading to measuring.
Downsides
The probe is throwaway code; daprd behavior may also change version-to-version (streaming subscriptions still evolving, dapr#8079), so the datasheet needs a daprd version stamp.
Confidence
90%
Complexity

Idea 2

Host the engine in the component — the WSL2 shape

deployment-shape
Description
Answer the inflight docs' second unknown by making the pluggable-component container be the PC JVM: a process embedding ProxyProcessor that implements Dapr's component gRPC service directly, talking to daprd over the Unix domain socket. This is Dapr's own sanctioned topology — a pluggable component is defined as a separate container beside daprd in the same pod — so the "two sidecars" smell dissolves: there is no PC proxy process anywhere in the chain, just the two processes a Dapr user already runs. The precedent is WSL1→WSL2: translating a foreign contract onto a different engine leaks semantics at every edge forever; hosting the real engine inside the boundary won. Credentials improve too: the Component YAML plus Dapr's secret store carry Kafka credentials to the component at Init, so they never travel an unauthenticated loopback wire — a genuinely better posture than the proxy's recorded R48 reversal ("the gap recorded rather than papered over").
Basis
direct: "their sidecar talking to ours is two sidecars, which is a smell; whether a component can host the engine directly is the question" (next-http-strategy-ideas.md §3); "The engine is built against this pair only — it never imports a transport class" (DispatchSink.java). external: Dapr pluggable-components architecture (separate container, UDS, Init metadata).
Rationale
Both halves of the deployment unknown resolve at once, and the choice templates every future adapter: "does this front-end host the engine or proxy to a sidecar" is expensive to reverse once operators have deployed either shape.
Downsides
A JVM inside the component container is a heavier image than Dapr's Go components — worth stating plainly rather than hiding. One security claim from ideation was cut here: UDS peer credentials authenticate the daprd↔component hop only — they relocate, not close, the KTD11 first-connection trust question. (Verification also found KTD11's own text has stale prose beneath its revised header — worth a small doc fix on the proxy branch.)

Idea 3

Dapr is a dialect, and native-vs-shim is an experiment, not an argument

engine-seam
Description
Architecturally, the adapter is one more encoding of the same engine seam: Dapr's component service wired to the same ProxyProcessor/DispatchSink internals the gRPC dialect uses — never a second implementation of ordering, retry, or offset logic. In the conformance suite it is one more (language, dialect) row: "more rows and no new scenarios". The frozen v1 protocol is untouched (a parallel service is a gain, not a change). Hold the honest counter-proposal alongside it: a thin Go shim speaking frozen v1 as "the twelfth client" (three processes per pod, zero JVM-image concerns, exercises the Go client scaffold). Frame native-vs-shim as the project's first Dapr ADR — and let the probe (idea 1) plus an image-size/operational comparison decide it, not taste.
Basis
direct: "No shard selection, no retry scheduling, no offset tracking. A client that grew any of those would be a second implementation of Parallel Consumer, and there would eventually be eleven of them, disagreeing" and "a new dialect is more rows and no new scenarios" (next-work-server-pitch-and-buyer.md §5, verified verbatim).
Rationale
Slotting Dapr into an architecture row that already exists means facade discipline, the conformance suite, and the freeze gate all apply unchanged — the difference between "small adapter" and "second implementation to keep in sync". Making the shape decision experimentally keeps the strongest alternative alive until evidence kills one.
Downsides
Running the decision as an ADR-with-experiment costs a little ceremony; the shim option, if chosen, reintroduces a third process and the two-sidecars shape idea 2 argues against.
Confidence
80%
Complexity
Medium
Idea 4

The stream is the lease; one retry owner

delivery-semantics
Description
Dapr's contract has no Heartbeat, no reconnect Manifest, no WorkerDied — but v1's degenerate form already covers it: "the connection is the session". Map PullMessages stream lifetime onto the lease: stream open ⇒ all dispatched records leased; stream close ⇒ that session's in-flight records return to scheduling "with their attempt counts unchanged"; late acks after re-dispatch are discarded by the existing epoch fence (SUPERSEDED_EPOCH). A daprd restart then costs a bounded-duplicate re-dispatch wave — the same class as a rebalance, documented rather than discovered. The second rule: PC owns retry, alone. Dapr's resiliency policies retry at the daprd layer independently; two retry machines diverge attempt counts and race the epoch fence. The component must document daprd-side retry as must-be-off and reject configurations that enable it.
Basis
direct: lease semantics ("returns that session's in-flight records to scheduling with their attempt counts unchanged"), ProxyProcessor.report() epoch check, WorkContainer.updateFailureHistory — all verified verbatim. external: Dapr resiliency docs confirm daprd retries "augment" component retries and can cause "repetitive clustering of messages".
Rationale
Shows at-least-once survives Dapr's thinner liveness model using existing machinery, and names precisely what degrades. Double-retry is the "quietly wrong on failure" defect class this product exists to kill — preventable only by deciding ownership before the first line of component code.
Downsides
This is bug-857 territory (the silent-stall/zombie-liveness class with three fixes and an open root cause) — it needs real design work, not a green light. The verifier added a wrinkle: Dapr supports one component serving multiple daprd instances, where "the stream is the session" gets murkier than the 1:1 case this reasoning assumes.
Confidence
65%
Complexity
Medium
Idea 5

The NC-pin degradation table as contract and launch artifact

delivery-semantics · positioning
Description
Electronics adapters bridging incompatible sockets ship a datasheet marking which pins are Not Connected — the honesty is the product. PC's report vocabulary is four-valued; Dapr's ack is binary. Publish the mapping as a first-class artifact, run the shared conformance scenarios end-to-end through daprd, and let the residue table be the component's documentation, the claims-gate evidence, and the regression suite at once. Launch by posting the results — with Dapr's own component conformance tests passing alongside PC's suite — into dapr#5946, the thread where the demand is already recorded. With no component registry, certification-style evidence substitutes for shelf placement.
PC verdictDapr surfaceStatus
Failure (retry consumed)ack_errormapped
Terminaldead-letter topic conventionmapped, convention-based
Released (no retry consumed)— (lease expiry only)degraded
Success.produce (produce-then-complete atomicity)— (app publishes separately via daprd)not connected — consume-transform-produce stays on the native proxy
Basis
direct: Success.produce is "the only sanctioned route for worker output" and completion defers until produce lands (ProxyProcessor ACCEPTED_PRODUCING) — verified verbatim; Dapr's pub/sub has no ack-linked publish, so the atomicity severing is architecturally correct. "The conformance suite is the load-bearing part, not the clients."
Rationale
Extends the project's core discipline — correctness as a test result, not an adjective — across a runtime the project does not control, exactly where silent semantic drift would otherwise live. It also satisfies the claims gate by construction: the announcement is the evidence.
Downsides
An honest table showing degraded rows is a gift to hostile skimmers; mitigated by the orthogonal-axes framing (idea 6). One demand citation was cut in verification: dapr#4629 is about crash-loss questions, not head-of-line blocking — only dapr/dapr#5946 supports the demand claim.

Idea 6

Ordered-concurrency positioning, codified once

positioning-adoption
Description
KIP-932 share groups are GA: Kafka now natively offers unordered concurrent consumption. "Concurrency beyond partitions" alone is a falsifiable claim from day one; the claim that survives is order-preserving concurrency — which nothing in the Dapr catalogue offers (existing FIFO components — SQS FIFO, ASB sessions, RabbitMQ single-active-consumer — all trade concurrency away to get order). Write the coupling-vs-concurrency axes into STRATEGY.md once ("Dapr solves a different problem, and here is which"), and let the Dapr component, the kafka-pixy comparison, and every future "aren't you just X" conversation cite it rather than re-derive positioning under time pressure.
Basis
direct: "They are orthogonal axes, not competitors… 'We are better than Dapr' is both wrong and easy to refute"; "These claims belong in STRATEGY.md if they survive scrutiny" (next-study-dapr-and-kafka-proxies.md, verified verbatim). external: KIP-932 GA in Kafka 4.2.0 (released 2026-02-17, independently verified); FIFO-component survey.
Rationale
Positioning wrong in public is expensive to walk back. The frame is reusable verbatim across every adapter, and the landscape shift that makes it urgent (KIP-932) has already happened.
Downsides
Minimal — a documentation change; the discipline cost is keeping the claim true as KIP-932 client support broadens through 2026.

Idea 7

Skateboard module: UNORDERED/KEY-only v0, capability-gated growth, demand-gated build

engine-seam
Description
Scope v0 to what Dapr can natively say: ack → Success (no produce), ack_error → Failure, KEY and UNORDERED ordering, ceiling from component metadata. Ship as an isolated opt-in alpha module exactly like the streams/connect previews, README carrying the experimental warning so the claims gate holds. Terminal, Released, produce-on-success, and reconnect Manifest are explicitly out of v0 — later additions ride the protocol's existing capability negotiation ("negotiated in the handshake, never inferred"). One hard detail: Dapr component metadata is stringly YAML feeding typed, safety-critical config — a misspelled ordering value silently falling back to UNORDERED is a correctness bug, so validation must reject, never default. Sequencing: bank the cheap compounding parts now (the probe, idea 1; the strategy codification, idea 6); gate the full build on demand per the project's own rule — "build the one somebody asked for, not the one that completes the matrix". Secondary payoff: component adoption becomes empirical demand data for which of the eleven native clients deserve investment.
Basis
direct: capability-entry negotiation and "no 'unlimited': the in-flight ceiling is always finite" (proxy.proto, verified); "demand decides" and the experimental-claims gate (inflight docs, verified); streams/connect preview-module precedent (roadmap).
Rationale
Converts the whole thread from study to running code inside one iteration — the fastest way to confirm or kill ideas 1–5 — while the module isolation and claims gate cap the blast radius of being wrong.
Downsides
A v0 that can't produce-on-success excludes consume-transform-produce workloads (the native proxy's strength); must be stated in the README to avoid disappointed first users.
Confidence
70%
Complexity
Medium
