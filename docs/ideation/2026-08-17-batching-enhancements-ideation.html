Grounding Context

Codebase Context. Batch composition in the Parallel Consumer is emergent, not designed. Records shard by ordering mode (ShardKey.of(): KEY → one shard per (partition, key); PARTITION/UNORDERED → one per partition). ShardManager.getWorkIfAvailable round-robins shards with a fairness iterator; ProcessingShard yields at most one record per shard per call in ordered modes (the break at ProcessingShard.java:149-154), then the flat list is chopped shard-blind into batchSize chunks (AbstractParallelEoSStreamProcessor.makeBatches/partition, :1045-1077). Consequences: KEY-mode batches contain distinct keys only by side effect; real batch size is capped by the number of eligible shards; a whole batch fails and retries as a set; PollContext stores records in a HashSet with no order. Config surface: batchSize (default 1, unvalidated), ordering, maxConcurrency (which silently multiplies: in-flight target = maxConcurrency × batchSize). No linger/min-size/bytes axis exists.

Prior art (trackers). confluentinc#266 same-key-only batches (open since 2022, mirrored astubbs#145); PR confluentinc#915 batchStrategy enum (SEQUENTIAL / BATCH_MULTIPLEX / BATCH_BY_SHARD — open, unreviewed, flagged in upstream-map.yaml as the most valuable user-facing feature in the queue); confluentinc#560/confluentinc#562 min-batch-size + linger (abandoned 2023 after a test-coverage review); confluentinc#551/confluentinc#373 “batching not working as expected” (root cause: the one-record-per-shard ceiling — “the documentation is the bug”); confluentinc#887 one bad record fails the whole batch and the identical batch re-forms every retry (no jitter on the static 1s delay).

External prior art. Kafka producer batch.size+linger.ms (count/bytes/time race); Kafka Streams Suppressed (KIP-328, per-key conflation); Akka groupedWithin/groupBy; Flink custom Trigger (pluggable-policy escape hatch); AWS Lambda ESM ReportBatchItemFailures (the reference per-record partial-failure design); DynamoDB BatchWriteItem (rejects duplicate keys per batch — the strongest distinct-keys precedent); SQS (count is a best-effort ceiling, not a target).

Learnings corpus. No batching-specific learnings exist in docs/solutions/ — this is a greenfield design area. Reuse existing vocabulary and instrumentation (Shard, ShardManager.getWorkIfAvailable, the confluentinc#857 under-served diagnostic) rather than inventing parallel concepts.

Verification. Every survivor’s direct: basis was spot-checked against the repo by a fresh-context verifier; two candidate clusters were refuted on a mis-identified clock and are recorded in the Rejection Summary.

1

Settle the composition-API shape before PR confluentinc#915 merges

config-api Confidence 85% Complexity: Medium (a decision, then a refactor)
Description
PR confluentinc#915 proposes a three-value batchStrategy enum, and its author’s own open concerns (UNORDERED+MULTIPLEX semantics; whether shard-yield and batch-grouping should be split) show the shape is unsettled. Five candidate shapes exist on a spectrum from simplest to most general, and choosing among them is a one-way door that determines how confluentinc#266, confluentinc#560, and every future batching ask lands — as a config value, a plugin, or another core PR. The fairness question confluentinc#915 leaves open (“how many records may one shard yield?”) is answered differently by each shape.
The candidate shapes
  • Single integer — maxRecordsPerShardPerBatch: 1 = today’s emergent distinct-keys behavior, N = same-key runs of up to N, MAX = today’s UNORDERED drain. Dissolves confluentinc#915’s enum and its UNORDERED-ambiguity question (UNORDERED already is the value ∞). Smallest test matrix.
  • confluentinc#915’s enum as-is — three named strategies; simplest to review, but each future ask adds a fourth value.
  • Declarative batch spec — maxRecords / minRecords / maxRecordsPerKey / maxDistinctKeys / maxBytes: the user’s literal “10 records, always distinct keys” is maxRecords=10, maxRecordsPerKey=1; confluentinc#266 is maxDistinctKeys=1; a bytes cap (Kafka-producer precedent) is one more field, not a new feature.
  • Compatibility relation — a user-supplied predicate/grouping key over records (default: shard identity), the freight-consolidation model. Covers the real ask behind confluentinc#266 (destination affinity — one DB per account — which correlates with key but isn’t a key rule) and tenant grouping, without the enum ever growing.
  • Two-stage factoring — an explicit shard-yield policy × batch-grouping policy split, directly answering confluentinc#915’s open architectural question; a per-shard fairness-debt quota (CFS-style) supplies the missing “how many per shard” rule.
Basis
direct: ProcessingShard.java:149-154 — if (isOrderRestricted()) { /* can't take any more work from this shard, due to ordering restrictions */ break; } (verified); ParallelConsumerOptions.java:451 — batchSize is the sole batching knob, entirely primitive/enum-typed. PR confluentinc#915’s author-flagged open concerns, quoted in the PR body. external: Flink’s GlobalWindows + custom Trigger as the pluggable-escape-hatch precedent; Kafka Streams Suppressed as strategy-object config precedent.
Rationale
The project is about to add its second batching option with two more queued behind it (confluentinc#560’s min/linger, confluentinc#266’s composition ask). Deciding the shape once — before confluentinc#915’s architectural review, which the fork’s own upstream-map.yaml says it needs — is the difference between one deprecation cycle and four. Every other survivor in this document either feeds this decision or depends on it.
Downsides
A shape decision delays merging confluentinc#915 as-is; the more general shapes (predicate, two-stage) enlarge the test matrix that rkolesnev’s confluentinc#562 review already flagged (transactional × all orderings × non-reactor). The integer shape is cheapest but can’t express byte caps or min-size — those would still need the spec shape later.

PollContext’s HashSet ordering is a confluentinc#915/#266 merge blocker

composition-policies Confidence 90% Complexity: Low–Medium
Description
PollContext hands the user’s batch as Map<TopicPartition, HashSet<…>> — no offset order survives. Today that is nearly invisible because ordered modes yield one record per shard per batch. The moment same-shard batching ships (confluentinc#266 / confluentinc#915’s BATCH_BY_SHARD), a user gets five versions of one account’s record in hash order — KEY ordering broken not by a race but by a hash bucket, and a batched DB upsert applied in that order is last-write-wins on the wrong write. Fix first: an offset-ordered, shard-keyed batch structure (e.g. Map<ShardKey, List<RecordContext>> + an order-preserving stream()), a documented ordering guarantee, and ordering assertions in the batch tests.
Basis
direct: PollContext.java:45,50 — Map<TopicPartition, Set<RecordContextInternal<K,V>>> records = new HashMap<>() / new HashSet<>() (verified verbatim). BatchTestMethods.java — assertions use hasSize(...) and AssertJ’s order-independent hasSameElementsAs; no ordering assertion exists anywhere in the batch tests (verified). external: CPU write-combining buffers — merging stores into one burst is only correct because program order within the line is preserved; the same invariant applies to merging same-key records into one batch.
Rationale
Any same-key batching feature is unshippable on an unordered container, which makes this a prerequisite for the most-wanted feature in the queue, not a cleanup. It is cheap to fix before the composition work and a breaking change after. Nobody has raised it on the PR.
Downsides
Changing the observable iteration order of PollContext is itself a subtle behavior change for existing users (though moving from “arbitrary” to “offset order” is strictly less surprising); touching the type signature may need a deprecation path for getByTopicPartitionMap().

Poison-isolation ladder: jitter → bisection → per-record manifest

failure-retry Confidence 85% Complexity: Low → Medium → High (three rungs)
Description
A staged roadmap that closes confluentinc#887 at three depths. Rung 1 — default-on retry jitter: DEFAULT_STATIC_RETRY_DELAY is a fixed 1s with no randomisation, so a failed batch re-forms identically forever; a small per-record jitter (derivable from retry count / key hash) is nearly free and the retryDelayProvider workaround proves it works. Rung 2 — poison-batch bisection: on failure, retry the batch as two halves, then quarters — a poison record is isolated in log₂(N) rounds while every innocent sibling makes progress, with no user-API change (Dorfman pooled testing; AWS Lambda ships this as BisectBatchOnFunctionError). Rung 3 — per-record failure manifest: let the batch function report which records failed (AWS ReportBatchItemFailures shape); only those re-enter retry, so the “same bad batch” can’t re-form by construction. Bisection remains the fallback for functions that report nothing.
Basis
direct: ParallelConsumerOptions.java:329 — DEFAULT_STATIC_RETRY_DELAY = Duration.ofSeconds(1), and WorkContainer.java:221 — retryDueAt = lastFailedAt.plus(retryDelay), no jitter (verified). The decisive find, verified verbatim: AbstractParallelEoSStreamProcessor.java:1403-1416 — runUserFunctionInternal declares intermediateResults, comments “capture each result, against the input record”, never populates it, and returns it empty. Batch atomicity is an unfinished feature, not a design invariant — the per-record correlation was started and abandoned. Also :1338-1341: the batch already splits into two outcome groups (stale vs active) and routes them separately. external: AWS Lambda ESM ReportBatchItemFailures; BisectBatchOnFunctionError (note: AWS offers it for Kinesis/DynamoDB stream sources, not Kafka ESM — the technique transfers, the citation is inspiration rather than a Kafka-native precedent).
Rationale
The dead intermediateResults code changes the cost estimate that killed the confluentinc#561/#562 class of work: the manifest is “finish an existing seam”, not “deep hot-path surgery”. Jitter alone only randomises which innocents suffer; bisection bounds their suffering at log₂(N) retries; the manifest ends it. Shipping the rungs in order gives users relief at each step while the deeper work proceeds, and the doc’s current weasel clause (“no guarantee they will all be in the same batch again”) becomes a designed guarantee: they deliberately will not be.
Downsides
Rung 1 changes default retry timing for existing deployments (needs a go/no-go, not silent shipping). Rung 2 interacts with ordering guarantees when splitting (halves must respect shard boundaries). Rung 3 is a public-API addition to the batch contract and needs the full ordering × transactional × adapter test matrix.

Batch telemetry + shortfall attribution — and ship the confirmed over-request bug fix now

observability-docs Confidence 90% Complexity: Low (bug fix) / Medium (telemetry)
Description
Batches are invisible in production: every metric in PCMetricsDef is per-record; batch sizes are computed and discarded in a DEBUG log (:1070-1074); a batch’s only “identity” is the first record’s offset stuffed into MDC (:1330). Add batch identity, a realised-vs-configured size histogram, distinct-shards-per-batch, partial-batch rate, and shortfall attribution — when a batch is short, say why (the four causes are enumerable in code: order-restriction break, couldBeTakenAsWork false, retry delay pending, queue empty), reusing the confluentinc#857 under-served diagnostic (ShardManager.java:279-296) that already computes most of it at DEBUG. That converts the recurring confluentinc#551/confluentinc#373 “batching not working” report into a log line users read on first run.
The confirmed bug (ship independently)
This ideation’s verification pass confirmed a real arithmetic defect in calculateQuantityToRequest (AbstractParallelEoSStreamProcessor.java:1093): the round-up uses target − modulo where filling the last batch needs batchSize − modulo. Worked example (verified): target=100, batchSize=30, delta=70 → modulo=10 → code requests 160; correct round-up is 90 — roughly a 2× over-request whenever the deficit isn’t a batch multiple. It survived because the only witness is a DEBUG log — which is the argument for the telemetry in one sentence.
Basis
direct: all verified by fresh-context spot-checks: the target - modulo arithmetic at :1091-1094 with concrete numbers; PCMetricsDef.java:23-61 per-record-only metrics with two batching-adjacent TODOs; the DEBUG-gated under-served diagnostic at ShardManager.java:279-296; MDC pseudo-identity at :1330.
Rationale
Every composition or triggering change in this document needs this signal to be judged: self-tuning needs fill rate, yield policies need shards-per-batch, and confluentinc#915’s review needs before/after evidence. Building telemetry first turns the API-shape debate (idea 1) from opinion into measurement — and the bug is immediate, shippable value found by looking.
Downsides
Metric cardinality needs care (histograms, not per-key labels); the bug fix changes request pacing, so throughput-sensitive deployments should see it called out in release notes.

Config interlock: batching-aware validate() and a derived-semantics startup line

config-api Confidence 90% Complexity: Low
Description
validate() checks nothing about batching. Verified end-to-end: batchSize=0 makes getTargetAmountOfRecordsInFlight() return 0, so WorkManager.getWorkIfAvailable(0) early-returns forever — a config typo produces a healthy-looking consumer that processes nothing (the same silent-stall symptom class as confluentinc#857, reachable from configuration). Add an interlock table: reject batchSize < 1; warn on structurally-futile combinations (PARTITION ordering with batchSize > 1 is a no-op the test suite itself encodes); and print one derived-semantics line at startup — “KEY ordering, batchSize 10, maxConcurrency 16 → at most one record per key per batch; in-flight ceiling 160.” Fold in the verified javadoc contradiction: ParallelConsumerOptions.java:304-310 claims 2×3 → “at most 15 records”; the code computes 6.
Basis
direct: ParallelConsumerOptions.java:473-477 — validate() is requireNonNull(consumer) + transactionsValidation() only (verified); the zero-throughput path through WorkManager.java:143 (verified); transactionsValidation() is the in-repo precedent for combination-rejection with a message naming both fields. external: takeoff-configuration warning systems — refuse the illegal state at the moment of commitment, not in a manual.
Rationale
confluentinc#551 was root-caused as “the documentation is the bug”; an interlock plus a startup line reaches users where the README did not. confluentinc#915 multiplies the option matrix, so the ruleset for illegal combinations has to exist before the matrix grows — and the silent-stall footgun is a production incident waiting on a typo.
Downsides
Rejecting previously-accepted (if nonsensical) configs is technically breaking; needs a clear error message and release note. The startup line must stay one line — verbose startup banners get ignored.

Unblock confluentinc#560 by deleting the knob: achievability-bounded triggering + Nagle self-clocking

triggering-sizing Confidence 70% Complexity: Medium
Description
confluentinc#560 stalled in 2022 on rkolesnev’s question: “does minimum batch size add any value over just adding Linger?” The code contains the answer neither side gave: under ordered modes the achievable batch size is capped by the number of eligible shards — the test suite itself encodes it (BatchTestMethods.java:155: “partition ordering restricts the batch sizes to a single element…”, verified verbatim) — so a plain linger would wait out its full timeout on every batch and deliver nothing. Two knob-free mechanisms follow: (a) achievability bound — compute maxAchievableBatchSize from eligible-shard count and stop waiting the moment a batch cannot grow; (b) Nagle self-clocking — submit a partial batch only when the worker pool would otherwise idle; when all workers are busy, hold and let it fill, because waiting is free while the user function is the bottleneck. Both signals already exist in the control loop (lastWorkRequestWasFulfilled at :980 drives real control-flow; getActiveCount() is already read). No timer, no new config to mistune.
Basis
direct: the BatchTestMethods comment and PARTITION no-op behavior (verified); lastWorkRequestWasFulfilled → checkPipelinePressure() → dynamicExtraLoadFactor.maybeStepUp() (verified as control-flow, not just logging) — the self-tuning precedent is already accepted in this hot path. external: Nagle’s algorithm (RFC 896) — batching clocked by acknowledgements needs no timer and degenerates to send-immediately when idle.
Rationale
This closes a three-year-old stalled feature by answering the exact review question that stalled it — and by removing the choice the reviewer didn’t want users to have to make. It also sidesteps the reason confluentinc#561/#562 died: no new option to validate across the transactional × ordering × adapter matrix.
Downsides
Verifier caveat (important): thresholdForTimeSpendInQueueWarning / addToSlowWorkMaybe measures time since last dispatch, only for already-dispatched work — it is not a pre-batch queue-dwell clock, so any residual linger semantics need a new clock, not a promotion of that one. Self-clocking changes latency behavior under load and needs benchmark evidence (which idea 4’s telemetry provides).

confluentinc#266 has two opposite answers — decide them jointly

composition-policies Confidence 70% Complexity: Medium–High
Description
The workload behind confluentinc#266 (“one DB per account — batch-insert per account”) has two structurally different solutions. Batch the same-key records: confluentinc#915’s BATCH_BY_SHARD — all N records for the account arrive in one batch, one DB round-trip. Don’t process most of them at all: conflate-per-key (Kafka Streams Suppressed / DynamoDB overwrite_by_pkeys semantics) — for last-write-wins state, only the newest record per key survives into the batch; superseded records auto-complete (offsets commit, side effects skipped). The seam is verified-local: ProcessingShard iterates its ConcurrentSkipListMap in ascending offset order and takes the first available container — taking the last (and completing the rest) is a change at the same point. For CDC/state-update streams the second answer is an order-of-magnitude larger win than the first; for append-semantics workloads only the first is correct. Choosing between them (or offering both) should happen with both on the table.
Basis
direct: confluentinc#266’s maintainer question (“new ordering mode, or an option enabled with key ordering mode”); ProcessingShard.entries as NavigableMap/ascending-offset iteration (verified). external: Kafka Streams KIP-328 per-key conflation; DynamoDB BatchWriteItem duplicate-key rejection plus boto3’s conflate-by-key mitigation — the industry pattern pair matching these two answers.
Rationale
confluentinc#266 is the oldest open batching ask (2022, still upvoted in 2026). Answering it with BATCH_BY_SHARD alone would ship the smaller win to the users whose real problem is redundant same-key work. Deciding jointly costs one design discussion; deciding serially costs a second multi-month cycle.
Downsides
Conflation skips user side effects for superseded records — safe only under a mode the user explicitly opts into and reasoned through (exactly-what-semantics needs care with transactions). It also interacts with retention/replay expectations, and both answers depend on idea 2 (ordering) landing first.
Sequencing note (from the cross-cutting synthesis): ideas 2 (ordering), 4 (telemetry), and 5 (interlock) are the floor that makes confluentinc#915’s architectural review measurable rather than opinion-based; idea 1 is the decision that review exists to make; ideas 3, 6, and 7 build on the settled floor. The one-line over-request fix in idea 4 is shippable today.
