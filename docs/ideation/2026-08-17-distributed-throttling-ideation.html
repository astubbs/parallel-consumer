Grounding Context

Codebase Context. The dispatch seam is ProcessingShard.getWorkIfAvailable: a tight per-candidate loop where two boolean gates — pm.couldBeTakenAsWork(wc) and wc.isAvailableToTakeAsWork() (isNotInFlight && !isUserFunctionSucceeded && isDelayPassed) — already skip records without blocking a worker. Retry deferral sets retryDueAt only on failure; the sorted RetryQueue feeds getLowestRetryTime() → getTimeToBlockFor(), the control loop's only wakeup calendar. Backpressure is separate: WorkManager.isSufficientlyLoaded() against targetAmountOfRecordsInFlight × DynamicLoadFactor drives BrokerPollSystem pause/resume of the whole assignment. ParallelConsumerOptions has exactly one Function-typed policy hook (retryDelayProvider); PCModule is the hand-rolled DI container with an explicit zero-dependency policy; core's compile deps are kafka-clients, zstd-jni, snappy-java, micrometer-core. The name RateLimiter is taken by an internal log-debounce.

Issue context (directive). astubbs#228 asks for cluster-coordinated rate limiting (the failure mode: N instances each assume they own the whole budget) and records the objection — a shared cache is a heavy runtime dependency for a Kafka-client-only library. Its 2026-08-15 comment argues the limiter belongs at the dispatch seam, composing with retry and ordering. confluentinc#766 is the real-world case: 400K RPS in, 50K RPS downstream capacity, 113 nodes on 100 partitions, CPU pinned, uneven load, and the maintainer answer "there is no support for distributed rate limiting in Parallel Consumer." It also reports pc_user_function_processing_time_seconds is inaccurate under Vert.x.

Prior art. The abandoned branch features/rate-limiting (e9f49d321, Oct 2021) is one commit: bucket4j wired locally into an example app, build-breaking pom properties, an infinite assertion-less test — and it policed (returned Mono.error) rather than deferring. Externally: Envoy's two-tier local-bucket + global-service split, Doorman leases, Kafka's own KIP-124 broker quotas, Netflix concurrency-limits (adaptive), and Karafka Pro — whose throttler is explicitly not cluster-coordinated and resets on rebalance. Nobody in the Kafka consumer-framework space divides a downstream budget using the consumer group itself.

Status of the libraries weighed in confluentinc#24 (2020's shortlist, re-checked 2026). bucket4j: the survivor — actively maintained (v8.19), with distributed backends grown well beyond the 2020 state: JCache (Hazelcast, Ignite, Infinispan, Coherence), Redis (Redisson/Jedis/Lettuce), JDBC, MongoDB, plus a lock-free async API. The operative caveat: every distributed backend costs a network round trip per permit unless batched — on an already-saturated fleet (confluentinc#766) a per-record check worsens the overload, so any integration must take the Envoy shape (local bucket, slow-cadence global sync). ratelimitj: dormant for years; out of the race. resilience4j: the 2020 ruling stands and has hardened — resilience4j#350 remains unresolved and the maintainers treat distributed rate limiting as out of scope; their limiter is in-memory by design. The standard JVM resilience library deliberately punting is evidence that PC filling the gap is differentiation, not duplication. Also noted (not in the original issue): redis-cell — a Redis module implementing GCRA with the whole bucket state in one key (CL.THROTTLE), a lower-overhead primitive than a DIY counter if a Redis-backed plug is ever built.

1

Partition-share budget: distributed limiting with zero new dependencies

coordination-substrate Confidence 85% Complexity Low
Description
Each instance derives its share of a global rate budget from consumer-group partition assignment: perInstanceLimit = globalLimit × (myPartitions / totalPartitions), enforced by a purely local token bucket. numberOfAssignedPartitions is already a public getter updated in the rebalance callbacks PC already implements; total partition count is reachable via the already-wrapped Consumer.partitionsFor(topic) (verified: currently called nowhere in core). The share recomputes automatically on every rebalance — the exact event a shared-cache scheme would need a separate protocol to detect.
Basis
direct: AbstractParallelEoSStreamProcessor carries @Getter private int numberOfAssignedPartitions, maintained in onPartitionsAssigned/onPartitionsRevoked/onPartitionsLost; verifier confirmed partitionsFor is unused-but-reachable. external: the research digest flags this as an open, PC-shaped gap — no Kafka consumer framework divides a downstream budget by group assignment (Karafka Pro's throttler is local-only and resets on rebalance).
Rationale
It answers both recorded blockers at once: the demand signal (confluentinc#766's 113-nodes-on-100-partitions overload, where per-instance limits are wrong by 113×) and astubbs#228's dependency objection — no shared cache, no round trips, no new runtime dependency. Instances with zero partitions correctly get zero budget.
Downsides
Partition-count share ≠ demand share: skewed partitions strand budget on lightly-loaded instances. The upgrade path when that bites is a demand-responsive lease allocator riding the group protocol's unused ConsumerPartitionAssignor userData channel (verified unused in core) — deferred because a custom assignor is real adoption friction, not zero-cost (see Rejection Summary).
2

Dispatch-seam throttle via availableAt deferral — shape, don't police

enforcement-seam Confidence 85% Complexity Medium
Description
Two changes that only work as a pair. First, a third predicate beside pm.couldBeTakenAsWork(wc) and wc.isAvailableToTakeAsWork() in ProcessingShard.getWorkIfAvailable — a token check that skips without blocking, exactly like today's gates. Second, generalise retryDueAt into availableAt with a reason (RETRY | THROTTLE), settable without recording a failure, so a throttled record parks in the existing sorted RetryQueue and the control loop's wakeup (getLowestRetryTime() → getTimeToBlockFor()) learns exactly when the next token arrives. Network QoS vocabulary: a shaper (delay), not a policer (error) — the dead branch policed (Mono.error(RateLimitExceeded)), which burns a retry attempt and poisons failure metrics.
Basis
direct: isDelayPassed() opens with if (!hasPreviouslyFailed()) return true; — the deferral predicate is already generic; only the setter is failure-coupled (verifier-confirmed: retryDueAt is written only in updateFailureHistory). reasoned: a gate without a wakeup signal degenerates to the control loop's spin-avoidance floor (Thread.sleep(1)) for the whole throttled period — busy-waiting instead of sleeping until the refill instant.
Rationale
This makes astubbs#228's "composes with retry — same mechanism retry backoff uses" argument literal at the data-structure level: one sorted calendar, one wakeup path, no second scheduler subsystem, ordering preserved because the shard remains the unit of both ordering and deferral.
Downsides
Touches the hottest path in the library; deferral-only throttling is insufficient alone (idea 4 explains why it must also reach the poller); limiter skips must register as a named category in the confluentinc#857 silent-stall diagnostics or correct throttling reads as a stall bug.
3

Little's Law controller: an RPS target becomes the in-flight target PC already enforces

enforcement-seam Confidence 80% Complexity Low–Medium
Description
Don't add a rate gate at all. Since RPS = in-flight ÷ latency, a rate target converts to a concurrency target: targetInFlight = targetRPS × observedServiceTime, recomputed continuously from the USER_FUNCTION_PROCESSING_TIME timer that already exists. The controller writes one integer — the in-flight target — and every existing enforcement mechanism follows: verifier-confirmed, the same value drives both the dispatch quantity calculation (calculateQuantityToRequest) and the broker-poller pause threshold (isSufficientlyLoaded).
Basis
direct: the maxConcurrency javadoc in ParallelConsumerOptions (verifier-confirmed verbatim): "if your quota is expressed as maximum concurrent calls, this works well. If it's limited in total requests / sec, this may still overload the system. See towards the distributed rate limiting feature for this to be properly addressed" — PC's own docs name the gap, and Little's Law is the conversion between the two dimensions.
Rationale
The only candidate whose enforcement reaches both dispatch and poll suppression with no new plumbing — so it cannot produce the unbounded-deferral failure mode (idea 4) by construction. It is also a pure controller: unit-testable without touching ProcessingShard.
Downsides
Feedback subtlety flagged by the verifier: under active throttling, observed latency includes queueing time, so a naive controller feeds back on itself — it must use service time, not sojourn time. Granularity is coarser than a per-shard token bucket (no per-key/per-destination limits). Depends on accurate timing, which confluentinc#766 reports is broken under Vert.x — the async-engine metrics fix is a prerequisite.

The throttling constitution: liveness beats the limit, plus two API corrections

failure-dynamics Confidence 90% Complexity Low (design doc)
Description
A short, pre-registered design contract that any winning mechanism must satisfy — settled before code, like freeway ramp meters whose queue-override relaxes metering when the ramp spills back onto surface streets. The clauses, each traced to verified code: (1) the limit is constitutionally soft — group liveness and offset-map health outrank it, with a metered, alarming breach path (precedent: isBlockingProgress already exempts the record holding up the partition); (2) the throttle must reach the poller — deferral-only throttling under a sustained 8× input mismatch grows the incomplete-offset set toward the DefaultMaxMetadataSize hard limit, whose overflow means replay (and there is no max-age detector for a deferred record — verified); (3) budget state is epoch-fenced like work is (partitionsAssignmentEpochs), and must step down — noting DynamicLoadFactor has no step-down path at all (verified), a defect class not to inherit; (4) limiter skips are a named category in the confluentinc#857 silent-stall diagnostics; (5) two API corrections to the anchor issue's own argument (verified): ShardKey.of sees only topic/partition/key, so per-destination throttling needs a separate key function; and batching runs after work selection, so batch-aware token cost needs reserve-then-settle.
Basis
direct: every clause spot-checked by the fresh-context verifier against the worktree: PartitionState's isBlockingProgress carve-out and metadata-size pressure branches; BrokerPollSystem's full-assignment-only pause ("Pause all assignments", asymmetric 1/sec pause limiter vs unlimited resume); no stepDown in DynamicLoadFactor; ShardKey and makeBatches ordering confirmed.
Rationale
Everyone designs a rate limiter as if the limit were the outermost contract. In PC it is not — liveness is, and PC has already encoded that precedence once. Writing the constitution first converts four latent production-incident classes into review checkboxes, and corrects the anchor issue's architecture claims before an API commits to them.
Downsides
Not independently shippable user value — it is the acceptance criteria for ideas 1–3 and 5–6. Clause 2 implies per-partition selective pause, a real prerequisite gap (today's poller can only pause everything).
5

Socket-and-plug: SPI in core, backends as extension artifacts

packaging-observability Confidence 85% Complexity Medium
Description
Core ships one small pluggable seam — the second Function-shaped policy hook after retryDelayProvider — and implementations ship separately: the zero-dep partition-share bucket (idea 1) as the built-in default, bucket4j/Redis/Hazelcast in an optional parallel-consumer-* artifact exactly as -vertx/-reactor/-mutiny isolate their framework dependencies today. Three signature constraints are the actual content: (a) non-blocking — Optional<Instant> notBefore(key, cost), never a blocking tryAcquire() (a backend that blocks the control thread is a liveness hazard); (b) reserve-then-settle — batching runs after selection, so a 100-record batch making one downstream call reserves on dispatch and settles actual cost on completion; (c) not named RateLimiter — that name is taken by the internal log-debounce, and "throttle" already means buffer-driven partition pause in the feature docs.
Basis
direct: docs/features/core-dependency-footprint.yaml: "Adding an integration artifact intentionally adds that integration's dependency surface"; retryDelayProvider confirmed as the only Function-typed option field; PCModule's zero-dependency comment; the Micrometer meterRegistry is the existing socket-and-plug precedent (core takes the interface, the user brings the backend).
Rationale
It resolves astubbs#228's recorded open question — "does the fork want this at all, given the dependency?" — by packaging rather than argument, with a pattern this codebase has already applied three times. It also fixes the exact way the 2021 branch died (bucket4j hard-wired into example apps). One interface additionally unifies the three "who owns the number" philosophies — operator-published, downstream-reported (429/Retry-After), and adaptive — as three implementations instead of three competing features.
Strategy menu (refined 2026-08-18)
The built-in implementations form a curated menu where each serves a distinct situation rather than being a different way of doing the same thing: partition-share (you know the number and PC is its only consumer), downstream-signal (the service reports — also the only strategy correct when non-PC clients share the budget), adaptive (nobody knows the number, or it shifts — idea 8), BYO bucket4j (exact cross-client enforcement, existing cache). Multiple active strategies compose by taking the minimum of their emitted ceilings, so any combination is safe by construction — partition-share as the prior with adaptive trimming below it is the natural stack. The enforcement mechanism (ideas 2/3) is deliberately not on the menu: it is internal plumbing, not user policy, and offering it doubles the maintenance surface.
Downsides
Public SPI signatures are one-way doors; the SPI alone delivers no throttling until at least the default impl (idea 1) lands with it. Distributed backends still carry the per-permit round-trip question (the Envoy answer — local bucket, slow-cadence global sync — belongs in the backend artifact's design).

Adaptive AIMD on rate: no configured number, no coordination

limit-specification Confidence 65% Complexity High
Description
Remove the number entirely. Each instance runs additive-increase / multiplicative-decrease on its own dispatch rate, backing off on downstream congestion signals (429s, timeouts, latency gradient). Chiu & Jain (1989) proved AIMD is the linear control law that converges to both efficiency and fairness among uncoordinated actors sharing a bottleneck — so the fleet divides the downstream's true capacity with zero cross-instance communication. Deliberately AIMD on rate, not concurrency: the maxConcurrency javadoc says concurrency is the wrong dimension for rate quotas, and confluentinc#766 already had concurrency capped (800) while overloading its downstream.
Basis
external: Chiu & Jain, "Analysis of the increase and decrease algorithms for congestion avoidance," Computer Networks 1989; Netflix concurrency-limits (Vegas/Gradient) as the JVM prior art, differing on the controlled dimension. reasoned: it is the only approach that stays correct when downstream capacity changes (deploys, autoscaling, noisy neighbours) and when the downstream is shared with non-PC clients — cases every configured-budget scheme silently gets wrong.
Rationale
The confluentinc#766 reporter's "known" limit (50K) coexisted with a pinned-CPU fleet — the configured number is usually wrong. Adaptive limiting is the strongest answer to "what does the user configure": nothing. Natural composition: AIMD as the fast local loop with idea 1's share as the slow prior, so instances don't cold-start from zero.
Downsides
Loss-based signals arrive after overload; latency-gradient signals need clean timing, and async-engine timing is broken today (confluentinc#766) — that metrics fix is a hard prerequisite. Convergence oscillates (sawtooth); harder to reason about and test than a static bucket; needs the step-down machinery DynamicLoadFactor conspicuously lacks.
7

Decorrelated jitter for the retry path

failure-dynamics Confidence 90% Complexity Low
Description
PC's retry delay is fully deterministic — retryDueAt = lastFailedAt + retryDelay, and a grep for jitter/randomness in the retry path returns nothing (verified). When a shared downstream throttles or fails, every affected record on every instance computes nearly the same due-instant; the RetryQueue's sorted head then wakes each control loop at that same moment and re-dispatches the whole cohort at once — a synchronized retry storm, within one instance and across the fleet. Add decorrelated jitter (AWS's variant) to the default delay computation.
Basis
direct: verifier-confirmed absence of any Random/jitter in WorkContainer and ParallelConsumerOptions. external: Brooker, "Exponential Backoff And Jitter" (AWS Architecture Blog, 2015) — decorrelated jitter measurably outperforms plain exponential backoff at high client counts; CSMA/CA's foundational result that deterministic backoff guarantees re-collision.
Rationale
The cheapest item on this list, independently shippable, and it improves the currently recommended workaround — the confluentinc#766 maintainer's advice was "let PC's retry/backpressure react to downstream errors," which is precisely the deterministic path that synchronizes today. It helps every user, including those who never adopt a limiter.
Downsides
Changes default retry timing (needs a release note); does not by itself address the sustained-overload case — it removes the storm harmonics, not the load.

Self-scaling: one adaptive controller replaces concurrency and rate configuration

limit-specification Confidence 70% Complexity High
Description
Added 2026-08-18, merging this ideation with the fork's oldest open ambition: astubbs#227 (mirror of confluentinc#21, "Dynamic concurrency control with flow control or tcp congestion control theory"). Instead of the user pre-selecting maxConcurrency — a number that is wrong in both directions: too low silently leaves throughput on the table (nobody files an issue for wasted headroom), too high floods the downstream (the confluentinc#766 case), and no static value stays right as conditions shift — one adaptive controller owns the dispatch budget, fed by three signals: latency gradient (step concurrency up until job time degrades, then contract), failures, and structured rate-limit feedback — the user function throws an engine-recognised exception (e.g. RateLimitExceededException(serviceKey, retryAfter)) when a downstream returns 429/overloaded, and the engine builds a per-service ceiling from it at runtime. Per-service limits thus materialize from feedback instead of config: a user function may call dozens of services depending on record data, each with its own limit, none declared anywhere. The effective budget is min(hard maxConcurrency cap if configured, configured rate ceilings, discovered per-service ceilings, adaptive capacity estimate). Off by default (experimental); a user may run self-scaling and a hard upper cap.
Basis
direct: astubbs#227 is open, labelled pr-available/next-feature-release, and already distinguishes this from DynamicLoadFactor (which sizes the buffer feeding a fixed pool, not the pool). Two abandoned fork branches hold real prior work: features/dynamic-concurrency-control @6f85eac41 wired Netflix concurrency-limits (Gradient2Limit/SimpleLimiter/BlockingAdaptiveExecutor as the worker pool) with a README section "Automatic Concurrency Scaling (self configuring)" and a mid-extraction to a parallel-consumer-core-auto-scale module honouring the zero-deps policy; feature/auto-tuning-pressure @f4aa09788 ("Wip! Experiments in self tuning") hand-rolled the same instinct into the backpressure system. Upstream twin: draft PR confluentinc#22 @ba6b71f10, closed unmerged in the 2023 sweep. external: Netflix concurrency-limits (Gradient2Limit has the built-in maximum the hard-cap composition needs).
Rationale
This subsumes most of the rate-limiting ask: when the downstream's limit is a capacity limit, adaptive discovery finds it without configuration, exploits bursts a static number would waste, and re-converges automatically when the PC group itself scales up or down (each instance's fair share shrinks or grows with membership — distributed rate limiting as an emergent property, no coordination substrate at all). The structured exception dissolves idea 4's ShardKey correction — the engine learns destinations instead of being configured with them — and its retryAfter feeds idea 2's availableAt deferral directly. Critically, a rate-limit signal is a deferral instruction, not a failure: it must not increment failure history or failure metrics. The one thing self-scaling cannot subsume: a contractual quota (a vendor that bills or bans at N RPS) is invisible to latency — a well-provisioned endpoint shows no degradation right up until it rejects you — so explicit ceilings (ideas 1/5) remain complements, composed by min(), not rivals.
Downsides
Experimental by nature; the old branch's own README warning stands (a contracting pool can strand timed-out jobs as duplicates downstream); requires the async-engine timing fix (confluentinc#766) as signal integrity; both prior WIPs have bitrotted (design references only); and the controller must not fight DynamicLoadFactor/backpressure — they control different variables (pool size vs buffer depth) but share signals, so the boundary needs stating up front.
Second dimension (2026-08-18)
Beyond per-instance concurrency lies instance count: PC never spawns instances itself, but can expose a suggested-total-instance-count metric — raised only after a PC-owned cool-down establishes that instance-local concurrency has plateaued while the workload is still behind, capped at partition count, with rebalance as the natural acknowledgement that infrastructure acted. Staged as a follow-on; working design lives in docs/inflight/next-auto-scaling.md.
Recommended build order

Skateboard first: observe-only metrics (compute and report would-be throttle decisions, fixing the async-engine timing gap confluentinc#766 exposed) → idea 1 (zero-dep share) enforced through idea 2 or 3, under idea 4's constitution — with idea 5's SPI as the escape hatch for bucket4j users and idea 6 as the later philosophy upgrade. Idea 7 ships independently, any time.
