Grounding Context

Codebase Context. The "classic intro performance test" is the README's Illustrative Performance Example, backed by VeryLargeMessageVolumeTest: high message volume, 0–5 ms random processing time, and the famous throughput-by-key-space chart — currently three hand-maintained Google Sheets embeds in the generated README.adoc. The proxy branch carries 15 client modules (cpp, dotnet, go, java-api, java-direct, java-grpc, java-harness, kotlin, python, ruby, rust, scala, swift, typescript) plus a conformance suite: a Java harness drives dumb language runners from a LanguageRunners registry via ProcessBuilder, the engine binding runs as control arm in every selection, ScenarioCoverageTest fails the build on unbound scenarios, and clients.yml gates deferred modules as green-as-skipped-with-reason, never silently green. An in-JVM mock-Kafka harness (ProxyHarness) runs real gRPC transport with no Docker at sub-10-second speed.

The decisive prior art is in-repo. docs/inflight/parked-testing-as-a-feature-for-the-clients.md (2026-08-15, owner-authored) is a ready-made fairness charter for exactly this matrix: compare each language against in-process Java, not languages against each other; report the sidecar hop honestly; publish a case we expect to lose; single-run figures are not evidence. Sibling parked notes cover batching-vs-plain-consumer (sweep, publish the crossover) and native-client comparisons. A documented measurement-contamination incident (core's junit-platform.properties leaking factor=20 into eight modules) already invalidated numbers on two branches.

Institutional learnings (docs/solutions/): broker-per-fork process isolation is the only proven fix for concurrent-Kafka-test flakiness; absolute wall-clock throughput assertions are the first casualty on 2-core runners; CI retries hide flakes and were removed project-wide; every matrix cell needs a three-state outcome (ran+measured / ran+found-problem / could-not-run) that fails closed; a stalled consumer at 0 records/sec must read as broken, not slow.

External context (web research, high value): gRPC's own cross-language benchmark (central driver + per-language WorkerService, proxy workers for languages that can't self-host) and OpenMessaging Benchmark (Java driver-api, YAML workloads, interval metrics) are close structural analogs. wrk2's fixed-rate open-loop load is the standard fix for coordinated omission. The franz-go vs librdkafka controversy (a linger.ms 0-vs-5 ms default confound) is the canonical config-parity failure. Continuous benchmarking tooling: github-action-benchmark, Bencher.dev, Conbench. Containerized CI numbers are for relative regression detection; headline numbers need pinned hardware.

Evidence layer: five scout dossiers (scenarios, comparison-arms, harness, ci-integrity, demo-presentation) under the run scratch directory; all load-bearing quotes were re-verified against origin/feats/proxy-requirements by a fresh-context verifier (18 sound / 3 weak / 0 refuted outright).

Perf is the fifth conformance scenario — one harness, engine-owned stopwatch

Description
Do not build a benchmark codebase. Build the matrix as a new scenario family inside the existing conformance harness: the LanguageRunners registry already knows every language's build command and binary path, ConformanceDriver already orchestrates concurrent runners, and the engine binding already runs as control arm. A perf scenario is a conformance scenario with a bigger seed list and a stopwatch — and the stopwatch lives engine-side: all throughput/latency timestamps are taken identically in the sidecar's gRPC layer for all 13 languages, so runners measure nothing (they already assert nothing). Arms become pluggable invocation strategies over one workload definition, exactly the refactor next-reuse-integration-tests-for-conformance.md already prescribes. Cell admission is fail-closed by construction: a perf cell may only exist for a (language, scenario) pair whose matching conformance scenario is green, enforced through ScenarioCoverageTest and the deferred-wave gating clients.yml already applies (green-as-skipped-with-reason, never silent green). Implementation note carried from review: new test classes extend BrokerIntegrationTest, never LoadTest/DbTest, whose static Postgres container is a documented flake tax.
Basis
direct: conformance README — "Runners assert NOTHING deliberately; Java harness owns what 'correct' looks like"; LanguageRunners.java registry (module path, build command, binary path per language); ScenarioCoverageTest fails the build on scenarios no client drives; next-reuse-integration-tests-for-conformance.md — "separate what is asserted … from how the user function is invoked (parameterise: in-process Java, proxy + Java client, proxy + a foreign runner)". external: gRPC's cross-language benchmark uses the same central-driver / dumb-worker split. All quotes verifier-confirmed verbatim.
Rationale
The repo's own diagnosed failure mode is duplicated per-language setup logic drifting into flakes. A second orchestrator would pre-commit that mistake at 13-language scale. Reusing the registry means every future language client inherits the matrix for free, and engine-side timing makes every cell's instrument identical — a language cannot mis-measure itself, which is TechEmpower's known gamed-cell failure inverted into structure.
Downsides
Couples the perf matrix to the conformance suite's release cadence and possibly widens the frozen proto surface if timing echoes need a new field (additions are allowed by the buf gate). The conformance module gains a second responsibility, which needs clear internal boundaries.

Charter-first: the fairness constitution is already written — adopt it

Description
Make docs/inflight/parked-testing-as-a-feature-for-the-clients.md the stacked PR's normative anchor and cite it in the PR body, the harness docs, and the chart captions, rather than rediscovering its rules mid-review. Its three binding rules for this matrix: (a) no language-vs-language axis of merit — each language's cells are normalized against its own serial baseline and against in-process Java, so the matrix publishes no cross-language throughput ranking; (b) the sidecar hop is reported as a first-class cost, never engineered out; (c) the no-ordering big-data-replay column where the plain consumer wins stays in the matrix permanently — publishing the case we expect to lose is what makes the favourable numbers credible. Single-run figures are not evidence.
Basis
direct: parked-testing-as-a-feature-for-the-clients.md (2026-08-15) — "Not languages against each other. A slow language looks bad for reasons that have nothing to do with this project… The number that matters is what the sidecar hop costs relative to in-process Java, per language" and "publishing a case we expect to lose. That is what makes the favourable numbers credible rather than selected". Verifier confirmed both verbatim.
Rationale
Every other survivor's design choices (ladder decomposition, ratio gating, losing-case column) are consequences of these rules. Anchoring the PR on the charter costs a paragraph and prevents the two failure modes external prior art warns about: a language shootout that generates flame wars (TechEmpower) and a config-confounded number that retroactively discredits the whole matrix (franz-go).
Downsides
Almost none — the charter constrains presentation, which forecloses a viral-but-toxic "fastest language" headline some audiences would engage with. That is the point.

The keyspace-sweep spec workload — the classic chart, five lines, three parameterizations

Description
Canonicalize the README's single-partition keyspace sweep as the spec workload — one named, versioned workload definition, three parameterizations, five arms, thirteen languages. The README already states the design rationale: a single partition makes plain arms structurally capped (~1×) while PC arms scale with keyspace, so the flat lines are the control that proves the sweep measures ordering, not I/O. The three scenarios are variants of one definition: big data replay = 0 ms delay at VeryLargeMessageVolumeTest volume (the honest losing case); slow process stage = 0–5 ms work driven at a fixed arrival rate, open-loop, with latency measured from intended send time (wrk2 discipline, so coordinated omission can't flatter concurrent arms); KS augment-and-republish = the existing StreamsApp two-stage shape measured end-to-end. Critically, both KS arms derive from one topology — StreamsApp already implements KS-preprocess-then-PC-consume, so "core KS" is the same topology with the slow stage inline and the PC stage a toggle; there is no dependency on the unlanded ks-on-pc-spike branch. The guarantee asymmetry (PC+KS runs outside the topology's exactly-once boundary) is encoded in the scenario schema and rendered on every chart, never a bare bar. The workload schema accepts only sweep ranges for batch size and commit mode — no single-value field exists to cherry-pick.
Basis
direct: README_TEMPLATE.adoc — "A single partition (simplifies comparison - a topic with 5 partitions is the same as 1 partition with a keyspace of 5)"; StreamsApp.java (parallel-consumer-examples/parallel-consumer-example-streams) — preprocess() then concurrentProcess() on one topology; kafka-streams-integration.yaml — "outside the topology's exactly-once boundary and state stores"; parked-perf-batching-vs-plain-consumer.md — "sweep batch sizes rather than picking a flattering one… publish the point where the curves meet — or do not meet". external: wrk2 / Gil Tene on coordinated omission; YCSB workload-as-config.
Rationale
This resolves the parked note's "naive throughput comparison is close to meaningless" objection without inventing anything: the project's five-year-old headline chart already is the ordering-constrained workload the fairness doc demands. One spec file generates the entire matrix, and the sweep-only schema makes the cherry-picked flattering number structurally impossible rather than merely discouraged.
Downsides
Fixed-rate open-loop injection is new harness machinery (the existing tests are closed-loop). Deriving both KS arms from one topology requires refactoring the example app into the harness. Sweeps multiply cell count — budget control comes from idea 8's tiering.

The attribution ladder — java-direct → java-grpc → foreign as a measuring instrument

Description
The client table already contains a deliberately built differential probe that nobody has run as one: java-direct ("never speaks the protocol" — the engine in-process) isolates the engine; java-grpc ("owns no sidecar spawn" — same JVM, speaks the wire) adds only the protocol; each foreign client adds only its runtime. Publish every language's result as a stacked decomposition — engine cost + protocol cost (java-grpc − java-direct) + language/runtime cost (language − java-grpc) — so sidecar overhead is a first-class column computed by the harness on every run, never a footnote someone remembers to write. Kotlin and Scala wrap java-grpc, giving a fourth rung (wrapper cost) for free.
Basis
direct: parallel-consumer-proxy-clients/README.md — java-direct "Never speaks the protocol - the engine in-process… the control arm for the shared API"; java-grpc "Owns no sidecar spawn"; parked-perf-against-native-kafka-clients.md — "Report the sidecar's cost honestly as part of the result rather than engineering it out of the benchmark. A number that hides the hop is not reproducible in a user's system." All verifier-confirmed verbatim.
Rationale
This answers the question every non-JVM adopter will actually ask PR astubbs#293 — "what does the sidecar cost me, separately from what my language costs me?" — and it satisfies the charter's honesty rule structurally. It also keeps cross-language comparison fair under idea 2: languages compete only on the component they control.
Downsides
Decomposition by subtraction assumes the rungs are additive; contention effects can make components interact, so the ladder needs an honesty note of its own. Requires the engine-side timing from idea 1 to be trustworthy at each rung.

The double-click demo surface — docs-as-data results, per-language facts panels, one-command reproduction

Description
Blessed runs commit their results as docs/data/performance-profile.d/<module>.yaml fragments — the same one-module-one-file convention module-maturity.d/ and testing-evidence.d/ already use, validated by bin/check-docs-data.sh. The README's chart and a standardized "performance facts" panel in each of the 13 client READMEs are generated from those fragments at process-sources time, retiring the three hand-pasted Google Sheets embeds. The panel is an energy-label: throughput ratio vs plain consumer, p99 at fixed rate, sidecar-hop cost, config fingerprint, hardware class, liveness verdict — identical format across languages so comparison happens on the reader's terms. A Go developer lands on the Go client README and sees the classic PC chart for Go. Reproduction is one command: bin/perf-matrix.sh with seed, arm/language selection, and self-classifying exit codes, modeled on the web-gui branch's dashboard-demo.sh contract (pattern, not shared code — that branch is unmerged). Chart captions say "reproduce with bin/perf-matrix.sh". The fragments migrate untouched to the parked #208 docs site later.
Basis
direct: docs/data/README.md — "the canonical, renderer-independent data for release documentation… bin/check-docs-data.sh validates the structure"; README_TEMPLATE.adoc hardcoded pubchart URLs (three confirmed); 11 per-language module-maturity.d files as the proven pattern; parked-perf-against-native-kafka-clients.md — "Reproducible means re-runnable by a sceptic… A benchmark nobody can re-run is quoted forever and corrected never."
Rationale
This is the user's actual ask — the double-click demo in each language — built on machinery the repo already trusts. Checked-in YAML makes every published number diffable in PR review, makes a missing or stale cell a build error instead of a silent gap, and the one-command script makes the skeptic-reproducibility requirement a shipped entry point instead of a doc footnote.
Downsides
Committed numbers go stale between blessed runs and need a staleness policy (scenario-version field). Chart generation at build time is new tooling in the README pipeline. The laptop script's numbers will differ from pinned-hardware numbers — the facts panel must print its hardware class prominently.

The live polyglot performance loop — all clients running, realtime results, on repeat

Description
Turn the matrix into a running application, not only a document: every language's demo container boots (mock mode by default, real broker or the user's own cluster on request), each already emitting reading statistics, and a web-dashboard aggregates those streams into one realtime view that cycles the three matrix scenarios — big data replay, slow process stage, KS augment-and-republish — and restarts in a loop. Attract mode for the proxy. This is composition, not construction: the language-proxy plan already commits every client to a containerized demo (R72) with three identical modes including mock (R73), already requires every demo to print records consumed, processing rate, and per-key spread (R77), and already requires proxy-vs-in-process latency to be measured and reported (R31); the feats/web-gui branch already has an embedded dashboard and a one-command dashboard-demo.sh that boots a broker, workload, and consumer fleet. The display honors the charter (idea 2) by never rendering an absolute records/sec leaderboard: each language races its own serial baseline, with the live sidecar-hop decomposition from idea 4 beside it. Contention (the repo's proven CPU-starvation failure mode) is handled by running all clients in parallel against mocks, or by a carousel spotlight that measures one language at a time while the rest tick over — the loop structure the idea wants anyway. Ships local-first as a bin/ app with the stacked PR; when the docs site (astubbs#208) unparks, this becomes the parked demo gallery's payload. The demo-app UI itself is owned by the parallel polyglot-demo ideation track (docs/ideate-polyglot-demo); this idea contributes the performance story, workload definitions, and fairness constraints.
Basis
direct: language-proxy plan (docs/plans/2026-08-14-001-feat-language-proxy-plan.md) — R72 "the demo ships as a container so anyone can run any language's demo"; R73 three-mode contract with mock; R77 "Every demo prints reading statistics - records consumed, processing rate, and per-key or per-partition spread"; R31 proxy-vs-in-process latency "reports both"; docs/inflight/parked-demo-gallery.md — "the gallery is deployment work over demos that already exist, not demo work"; feats/web-gui:bin/dashboard-demo.sh. (Added in discussion after the verification pass; these quotes were read directly from the plan and parked note this session, not through the run's verifier.)
Rationale
This may be the strongest possible answer to the actual ask — the double-click demo per language before merging PR astubbs#293 — because it demonstrates instead of reporting: a visitor watches eleven languages doing key-ordered concurrency with live numbers, rather than reading a chart about it. Every constituent is an existing commitment or branch, so the marginal build is the aggregating view and the loop driver — and it gives the liked-but-parked gallery idea the payload that was missing when it was parked.
Downsides
Head-on charter tension if the display drifts toward a language leaderboard — the fairness framing must be designed in, not bolted on. Parallel contention corrupts numbers on one machine (mock mode or carousel is mandatory, and mock-mode numbers must be labeled for what they are). Live on-screen figures get screenshotted and quoted — render ratios and shapes with the hardware class printed, and leave absolutes to the blessed docs-as-data pipeline (idea 5). Highest coordination cost of the set: spans this track, the polyglot-demo track, and the unmerged web-gui branch.

The trust architecture — config fingerprint, provenance stamp, saboteur cell

Description
Three mechanisms that make every published number machine-attested. Parc fermé: one canonical scenario definition generates every arm's effective config; before a cell records anything, the harness collects each arm's resolved config (the proxy's negotiated intersection, the built ParallelConsumerOptions, raw consumer props), canonicalizes the shared knobs, and hashes a fingerprint — mismatched fingerprints void the cell, and the fingerprint is published beside the number. Provenance: every result row records effective JUnit parallelism factor, forkCount, hardware class, git SHA, scenario version, and config hash, and the harness asserts its own isolation before publishing — the junit-platform.properties leak silently ran eight modules at factor=20 and invalidated two branches' measurements. Saboteur: every full run includes a deliberately degraded arm that must measurably lose and a stall-rigged cell the pipeline must report as "stalled" (per-10-second progress windows distinguish slow from dead); if the saboteur passes, the run is void.
Basis
direct: proxy Configure proto (27 fields) with defaults diverging from core (proxy UNSPECIFIED = "proxy picks" vs core KEY ordering / 16 threads / 5 s commit); branch-parallel-measurement-contamination.md — "ran at factor=20 regardless of their own ${parallel-tests} setting"; HarnessScenario.java — "A harness that goes green when the client is broken would go green for ten languages at once"; the conformance suite's negative-control race was "found by actual sabotage testing". external: franz-go's linger.ms confound; motorsport parc fermé and railway dead-man's-vigilance as structural analogies.
Rationale
With 27 tunables × 5 arms × 13 languages, an unpinned config divergence is a certainty, not a risk — and one confound retroactively discredits the entire matrix. The repo has already paid for both other failure modes (contaminated measurements, silent stalls); this bakes their prevention into the schema on day one instead of retrofitting after the first hidden failure.
Downsides
Fingerprinting three different config surfaces into one canonical form is fiddly and needs maintenance as knobs are added. The saboteur cell adds permanent run cost. Voiding cells on mismatch can block publication on a technicality — needs a clear override-with-disclosure path.

Two-tier measurement — ratio-gated PR lane, pinned-hardware headline lane

Description
Split the matrix into two lanes with different physics. The PR lane runs on shared runners and therefore gates only on ratios: the plain-consumer arm is co-scheduled inside every cell's job as a standard candle, and assertions are "speedup vs serial ≥ floor" / "sidecar tax ≤ ceiling" — both arms see the same noisy machine, so the quotient is stable where the absolute number never is. Cheap relative-regression signal can come from the mock-Kafka ProxyHarness path (no Docker, sub-10 s). The headline lane produces the absolute numbers for the README/demo on pinned hardware (the self-hosted 16-core runner or nightly cron), appending to a trend view; only its blessed results feed performance-profile.d. A nightly full 5×3×13 run plus touched-cells-only on PRs (reusing the deferred-wave gating) keeps cost bounded.
Basis
direct: pr-highcpu-fast-feedback.yml — "accurate benchmarking belongs in a separate isolated/on-demand run" (verifier-confirmed verbatim; this corrects the generation-time claim that the perf lane is excluded from CI — it is in fact a required PR gate today, which strengthens the case for separating gating from measuring); ProxyHarness — "no broker, no Docker, sub-10-second unit-test speed"; learnings — absolute wall-clock assertions are the first thing to break on 2-core runners; the no-retry policy. external: containerization measurably distorts absolute numbers (CI = relative regression only); github-action-benchmark / Conbench for trend dashboards; astronomy's standard-candle pattern.
Rationale
This is the only assertion shape that survives shared-runner noise under the repo's no-retry discipline — an absolute gate would either flake constantly or get quietly loosened until meaningless. It also honors the external consensus that CI numbers and headline numbers are different products.
Downsides
Largest infrastructure footprint of the set: nightly cron, trend storage, and a pinned-hardware lane the team must own. Mock-Kafka regression signal doesn't exercise the real broker path, so it can miss broker-coupled regressions. Ratio floors still need calibration to avoid their own flakiness. Confidence is Medium because the two-lane split reshapes existing required checks, which is a team-level CI decision.
PR lane — every push
  • shared runners; mock-Kafka fast path
  • plain-consumer candle co-scheduled per cell
  • gates on ratios only; no retries
  • touched cells only; deferred rows skip with reason
Headline lane — nightly / on demand
  • pinned hardware (16-core self-hosted)
  • full 5 arms × 3 scenarios × 13 languages
  • absolute numbers; trend dashboard
  • blessed results → performance-profile.d
